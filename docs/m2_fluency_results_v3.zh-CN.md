# M2 流畅度结果 v3：第 3 步（Thinker 训练）与第 4 步（Talker 语速）

方案：[m2_fluency_plan_v3.zh-CN.md](m2_fluency_plan_v3.zh-CN.md)，含执行中的修订和读写时机文献。

试听页：
- 三版整场连续对比（M2 / v2 / v3）：https://claude.ai/artifact/RuSQpS5FoemNvDcxm6r2XV
- 训练数据审核：https://claude.ai/artifact/MrPjHX4uaBkDX4JzSbxG64

所有训练数据都来自 UniST，RealSI 和 ACL 只用来测试。

## 结论

1. **第 4 步有效，不需要训练。** Talker 的 speed token 本来就能控制语速：加快 6 档约快 10%，ASR-BLEU 基本不变（±0.3），UTMOS 只降 0.03–0.07；播放端 WSOLA 加速 1.1 倍要降约 0.2。原来测到“没有作用”，是因为推理策略每次都要求正常语速。
   - 新策略 `--speed-policy queue`：按每块写入时的积压选 speed token。
   - 推荐的 v3 配置：原 Thinker + 提交卫生 + 口语清洗 + 按积压选语速 + 播放端 S1 + 1.2 s 缓冲 + 块内静音压缩。偏置按“ASR-BLEU 不低于 M2”选定，结果见下表。

   | 方向（v3 的偏置） | ASR-BLEU（对 M2） | 逐句 LAAL | 突然停顿 / 分钟 | 扎堆比例 | 连续 LAAL |
   |---|---|---|---|---|---|
   | 英→中（偏置 1） | +0.56 | 1.77 → 2.01 s | 4.47 → 2.38 | 42% → 24% | 4.46 → 3.29 s |
   | 中→英（偏置 −1） | +0.26 | 1.70 → 1.68 s | 4.72 → 1.32 | 44% → 27% | 3.90 → 2.53 s |

2. **第 3 步（重训 Thinker 改变读写时机）没有带来“同等延迟下更好”的结果。** 三种训练标签都把模型推向“更晚开口、质量更高”，基本沿原来的延迟–质量曲线移动：
   - v4：句首前缀约束 oracle，句首行整体加倍；
   - v5：只加强被延长的句首目标；
   - v6：用 Thinker 自身似然给出每个词的最早可写时刻，即 Hibiki / BS-SiMT 式的对齐标签。

   和同偏置、不训练的 SQ 版本做配对检验，v4 的差异都不显著（+0.09 ~ +0.39）。v6 是唯一在流畅度上有额外收益的：
   - 中→英偏置 −0.5：ASR-BLEU +1.94（显著），有 ≥1 s 停顿的句子 35.3%，所有配置里最低；连续评测里扎堆比例从 31% 降到 19%。
   - 代价是逐句 LAAL 2.19 s，比 M2 高约 0.5 s，连续 LAAL 也更高。
   - 可以作为“质量和连贯优先、可以多等 0.5 s”的备选配置。

3. **为什么训练没解决句首等待。** 规则介入之前，Thinker 的第一个草稿中位数在第 1.0 s 就出现了，67%–86% 的句子在 1 s 内就有内容。真正的瓶颈是：
   - 读取窗的颗粒度（0.5 / 1 s）；
   - 我们自己的“最小块长”规则把句首这 3 个字或词扣下了。

   放宽首块最小长度能把中→英首次开口提前 1 s，但随后的空隙增多，ASR-BLEU 也没有提升，所以不采用。

4. **推理侧的两个尝试无效：**
   - 句首投票（TAF / RALCP）：英→中 −0.79 BLEU，中→英持平，停顿不减；
   - 放宽首块最小长度：见上一条。

5. **对 Talker 的建议：** 继续用原生 speed token 控制语速。播放端变速只作为跨句积压的兜底，只加速、不放慢、上限 1.1 倍。

## 4. 数据与审核

- **同传风格改写**：试验未通过，句首一致率 64% → 62%，已放弃。
- **前缀约束句首 oracle**：初版审核发现三类坏样本，严格过滤后通过，最终采用 4,403 + 3,687 条。
- **似然对齐标签**：12,000 句全部保留，过早可写的比例 ≤0.4%，审核通过。
- **训练配置**：都是在原版 Qwen3-Omni-30B-A3B-Instruct 上训练新的 LoRA，配方和 op_v3 相同，取第 200 步（v4 另评了第 400 步）。

## 5. 建议

- **采用 v3 推理配置作为默认**：英→中偏置 1，中→英偏置 −1，按积压选语速，播放端 S1 + 缓冲 + 块内压缩。它满足“ASR-BLEU 不降”，突然停顿和扎堆都明显减少。
- **v6 作为可选的质量优先档**：BLEU +0.9 ~ +1.9，停顿最少，但延迟约 +0.5 s。
- **后续方向**：读写时机只靠 SFT 标签很难在同等延迟下取得优势；剩下的停顿约 40% 来自“新句未开口”，主要受读取窗颗粒度限制。可以考虑：
  - 用 v6 的标签做偏好优化或带 BLEU 门槛的强化学习（方案中的做法 5、6），专门惩罚停顿；
  - 缩小读取窗（例如 0.25 s）并配合播放缓冲。
