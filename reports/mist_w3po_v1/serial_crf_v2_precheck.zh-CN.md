**怎么读这个 GO**
1. 后验**没有**钉在标签上（不同于 1′ 预检的 96%）。退火到 τ = 0.5 后，多条目读上的条目平均有 18.5% 的质量在"推迟 1 读再补写"上。
2. 但这个均值集中在少数条目上：τ = 1 时中位数只有 0.013，约 10% 的条目推迟质量 ≥ 0.5，其余接近 0。每个窗口标签路径的后验中位数是 0.97（τ = 0.5）和 0.999（τ = 1）。即大多数窗口上 v2 与 C0 几乎相同，信号主要来自退火和少数模型本来就偏好推迟的条目。τ = 1 的均值 0.117 也高于 0.05，所以 GO 不取决于 τ。
3. 最终读协议几乎不影响 S2（dev 0.191 → 0.185）。
4. 进入推迟状态后，下一读开头打开被推迟的 m 的概率与它在标签路径上被打开的概率相同（配对差中位数约为 0），一开读就 `<wait>` 的概率只有 0.006。这与 D3 一致：推迟状态本身不是陷阱。
5. **局限（要诚实）**：§13.10 规定读内按规范顺序写，所以格里被推迟的条目在下一读**总是排第一**，而这正是 v8 已经能补写的情形。`serial_crf_precheck.zh-CN.md` §12.5–§12.6 推断的失败链是"下一读先写新到期项，再在 `<wait>` 前放弃 m"，这种顺序不在这个格里。所以 v2 训练能否减少在线解码中的漏译，这次预检**不能**回答。S1 说明 41.7% 的重叠短漏译确实先经过了"推迟"；但推迟之后在哪一步丢失，需要在线逐读轨迹才能确定（本次未做）。

## 1. 实现细节与判定规则（在任何 v2 结果之前提交）

代码：`experiments/mist_w3po_v1/crf/precheck_serial_v2.py`，测试 `crf/test_precheck_serial_v2.py`（14 个 CPU 测试，`__main__` 运行器）。判定常数写死在脚本里：`TAU = 0.5`，`S1_STOP = 0.30`，`S2_STOP = 0.05`。

### 1.1 格（§13.10 原样）

- **条目**：sched 记录里的块（每块是一个闭合的 G-STAR 段）。同一说话人（slot；每个窗口里 slot 与说话人一一对应，已核对）的条目保持标签顺序。
- **松弛 1 读**：ρ(c) ∈ {ρ_lab(c), ρ_lab(c) + 1}；最终读的条目不能推迟。
- **状态**：已提交集合 A。松弛为 1 时，第 r 读之后 A_r = {ρ_lab ≤ r − 1} ∪ D_r，其中 D_r ⊆ B_r = {ρ_lab = r} 是按时提交的部分，并且在每个说话人内是标签顺序的前缀（各说话人的下闭集）。最终读 D_{R−1} = B_{R−1}。
  - 所以 §13.2 的集合状态递推在松弛 1 下就是 D_0, …, D_{R−1} 上的线性链。每读状态数 = Π_k (n_k + 1)。
- **历史**：h_r = κ(A_{r−1})，κ 用修正后的键 (ρ_lab, 源终点, 源起点)。κ 只依赖集合：被推迟的条目在之后的历史里出现在它的**标签位置**。
- **读 r 写出**：W_r = (B_{r−1} \ D_{r−1}) ∪ D_r。待补写的条目必须在本读写出；按规范顺序写（先待补写的，再 D_r，因为前者 ρ_lab 更小），然后是 e_r（`<wait>`；最终读为 `<eos>`，且像 Engine.read 一样在 softmax 前屏蔽 `<wait>`）。
- **势函数**：ψ_r(D_{r−1} → D_r) = log p_θ(规范顺序的 W_r ⊕ e_r | x≤t_r, c = "", κ(A_{r−1}))。
- **后验**：q_τ(路径) ∝ exp(τ Σ_r ψ_r)。log Z 用前向递推精确计算；τ = 0.5 预登记，同时报告 τ = 1。
- **无选择的读不打分**：只有一个上下文、一个写集的读（例如 B_{r−1} = B_r = ∅），对所有路径加同一个常数，后验不变，所以不做前向。报告的 log Z 是"自由读"的 log Z。测试验证了：自由读 log Z + 这些常数 = 完整 log Z，路径质量逐条相同。

### 1.2 规范顺序：S3(a) 在上 GPU 之前发现的缺口

- S 的构造键是 (commit_ms, 源起点)，其中 commit_ms = min(源终点 + 1 s, 窗口末)（`build_sched_windows.py` 第 92、99 行）。
- 在**非最终读**的每个块上，commit_ms = 源终点 + 1 s（dev 6,995 块、train 57,391 块全部如此），所以预登记的键 (ρ_lab, 源终点, 源起点) 与 S 的构造键给出完全相同的顺序。**每个历史都只含非最终读的块**，因此 κ 的历史与预登记完全一致。代码在每个上下文都断言这一点（`context()`）。
- **最终读内部不同**：构造把 commit_ms 截到窗口末，S 在最终读里按起点排；预登记的键按终点排。若照搬，最终读自己的条目在 dev 4.3%（145 / 3,366）、train 4.1%（1,150 / 27,953）的窗口里会被排成与 S（也就是 v8 / C0 的训练目标）不同的顺序。
- **处理**：写出顺序用 kap = (ρ_lab, commit_ms, 源起点, 块序号)。它在最终读以外与预登记的 κ 逐位相同，在最终读内与 S 相同，所以标签路径在**每一次读**（历史和写集）都等于 S。这是对预登记的最小补充，只影响最终读自己条目之间的顺序；在看到任何 v2 结果之前写下。

### 1.3 打分协议（修正后的基线：最终读 P 完整可见）

- **train 窗口**：最终读给整窗 P（没有关闭检测时刻）。
- **dev 窗口**：用 `evaluation/online_decode_finalpost.py` 的 `final_cut_ms`，即 `--final-read-post close_detect` 的规则 cut = max(t − 1.04 s, min(t, close_detect − 1.04 s))。
  - 本预检的 dev 窗口是**参考窗口**（`sched_dev_v1`，与 v1 预检相同），也没有检测器时刻。所以取该规则不晚于 t 的上限（close_detect − 1.04 s ≥ t，即在线 dev 窗口 93.6% 的情形）：cut = t。
  - 结果是窗口内所有完整的 80 ms 帧都可见，只有跨过窗口末的最后一个不完整帧被掩掉。与整窗 P 的差别最多一帧（测试核对）。
- 非最终读不变（t − 1.04 s 之后的 P 置零）。
- 最终读另按**旧协议**（与其他读一样掩码）打一遍，用于"新旧协议下 S2 的差别"（只报告）。
- 引擎路径与 v1 预检相同（`Engine.from_merged`、`audio_embeds`、`Prompter.ids`、左填充 + mask）。新协议的最终读用 `full=True` 加上述 P，`akey` 带协议名，避免共享说话人流的嵌入。

### 1.4 前向的组织

- 每个（读，上下文）做**一次**前向，续写为规范顺序的"待补写 ⊕ 全部 B_r"。在每个条目边界读 log p(e_r)，就得到所有"按时部分是 B_r 的规范前缀"的写集。
- 不是前缀的写集另做前向：按最大集合贪心覆盖，每个状态恰好属于一个前向的一个边界（测试核对）。
- 样本规模（计划）：dev 1,387 次新协议前向 + 193 次旧协议最终读；train 2,339 + 299。

### 1.5 判定规则（写死在代码里）

- **S3 精确性**（CPU）。不通过 → 先修代码，不上 GPU。每个打分进程在加载模型前对自己的窗口再查一遍 (a)。
  - (a) 标签路径（所有 D_r = B_r）上，第 r 读的历史 ids == S_ids[:β_{r−1}]，写集 ids == S_ids[β_{r−1}:β_r]，对 sched_v1 和 sched_dev_v1 的**全部**窗口的每一次读；另外 v1 的 κ 测试也要通过。
  - (b) 前向的 log Z、每条路径的质量、每读状态边际、每个条目的推迟边际，都与**暴力枚举**一致（容差 1e-9）。枚举独立于格的状态：直接枚举所有 ρ 赋值（每个说话人内非降），历史和写集都从赋值直接构造。用于随机合成实例，以及样本中可推迟条目 ≤ 10 的所有真实窗口（假 log 概率，是整个前缀的确定性函数）。跳过无选择读的版本也要一致。
- **S1 覆盖率**（CPU，v8 正式参考解码 `dev_v8_ctx0_guard_s8`）。
  - 人群：dev 所有 ≤1 s、ov50（其他说话人覆盖 ≥ 50%）、**没被召回**（打分器 recalled() 为假）的单元，即检查 A 的 295 个。打分器状态由 `diag_order_attr.run_scorer` 取得，短单元召回计数与 `score_text.json` 逐项一致（断言），人群与检查 A 的已存行逐个一致（断言）。
  - 应写窗口 w、应写读 t_due：与检查 A 相同。w 是与单元时间重叠最多的在线窗口；t_due 是第一个满足 t ≥ (b − w.start) + 1 s 的读，没有则取 w 的最后一读。
  - **"u 在 t_due 被写出"**：w 中有一个在 t_due 提交（write_ms == t_due）、文本非空的段，它的源区间放宽 2 s 后与 u 重叠，规范化文本以 u 的规范化参考开头或结尾，而且不能被它所映射说话人的其他已评分句子解释掉（检查 A 的文本匹配规则；**不论说话人标签**）。
  - **推迟发生（DEFERRAL）当且仅当**同时满足：
    1. t_due 不是 w 的最终读；
    2. w 在 t_due 提交了至少一个文本非空的段（"别的条目"）；
    3. u 没有在 t_due 被写出。
  - S1 = 推迟数 / 人群数。**S1 < 0.30 → 停止。**
  - 其余情况分类报告：DUE_FINAL、U_WRITTEN_AT_DUE（例如在应写读被写成别的说话人）、NOTHING_ELSE_WRITTEN_AT_DUE、NO_WINDOW。
- **S2 信号量**（GPU，dev）。
  - 人群：ρ_lab(c) 不是最终读（可推迟），且所在标签读 |B_{ρ_lab(c)}| ≥ 2（多条目读）的条目 c。
  - S2 = 这些条目上 q_{τ=0.5}(ρ(c) = ρ_lab(c) + 1) 的均值。松弛为 1 时，每次推迟都在下一读写出，所以这就是"推迟 1 读后补写"的后验质量。
  - **S2 < 0.05 → 停止**（v2 约等于 C0，没有训练信号）。
  - 说明：被比较的路径写出**完全相同的 token**，只是位置不同，内容概率的绝对值相互抵消。所以它是调度后验，不是 P2 那种包含整句参考译文概率的量。
- **GO** 当且仅当 S3 通过、S1 ≥ 0.30、S2 ≥ 0.05。

### 1.6 只报告

- τ = 1 时的 S2；旧最终读协议下的 S2（τ = 0.5 和 1）。
- **推迟状态下的结构开段概率**：每个有待补写条目的上下文，m = 规范顺序中的第一个待补写条目，在该读开头的 p(说话人 token) 和 p(说话人 token) × p(起始时间 token | 说话人)，以及该处 p(e_r)。对照是同一个 m 在它的标签读、标签路径上（前面的条目写完之后）的开段概率。
- S2 的子组：多说话人读、≤1 s ov50 条目、所有可推迟条目（含单条目读）；把最终读条目按 0 计入的另一种人群。
- 格规模、前向数、运行时间、显存。
- 对已用最终读因果 P 重解码的 `dev_v8_ctx0_guard_finalpost_s8` 也算 S1（只报告）。
- 运行检查（不是判定规则）：标签路径的 ψ 与 v1 预检已存的标签顺序 ψ 对比（非最终读协议相同；最终读用旧协议的分数）。冒烟门槛：读级 |Δψ| 中位数 < 0.5、最大 < 5 nats（v1 两次运行之间是 0.26 / 2.97）。
