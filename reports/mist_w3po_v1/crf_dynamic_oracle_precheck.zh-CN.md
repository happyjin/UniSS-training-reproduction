**怎么读这个 STOP**
1. **停在覆盖函数上，不在方法本身。** 残差格和 oracle 的数学部分是精确的（O3）。轨迹重建、规则与打分器的一致性也都精确（O1 i–iii）。没过的是"模型到底写没写某个条目"这个判定：人工看，171 个判定里错了 23 个。
2. **错误方向对 O2 不利。**
   - 规则判"未覆盖"的 58 个判定里错了 14 个（24%）；判"已覆盖"的 113 个里错了 9 个（8%）。
   - 把已写的条目当成"待写"会制造假的 pending 状态。50 个抽样状态中有 13 个含这种假待写条目，其中 10 个的待写条目全是假的，也就是说这些状态本不该进入 O2 人群。
   - oracle 会在这些状态上要求"再写一遍"，直接抬高 D。所以就算现在跑 O2，D 也无法解释。
3. **错在哪里**（§2.3）：
   - 打分器把一个完全正确的短回应（"Yeah."、"Yes."）记到同一说话人相邻的另一句上，规则 (a) 又把它"解释掉"（3 例）；
   - 改写或同义词，文本规则匹配不上（"For double check." 对 "To double check, so that"，"Like a mobile phone." 对 "Like phones."，"Yeah" 对 "Yes" / "It's okay"）；
   - 错标的短回应和问候（"Hello." / "Hey." / "Yeah." 标到别人名下）——设计上应算覆盖，但短单元只用 (a)、(b)，(a) 的严格词面匹配接不住；
   - 反方向：打分器按时间记分，把垃圾输出或别的句子的重复记成了覆盖（"T. i. d. television."，"Transparent or yeah." 被算作 "That's cool."）。
4. **能改，但必须重新预登记。** 可能的改法见 §3。按规则，本次不再跑 O2，也不改规则后重判。

O2 的状态已经生成（2,231 个，共 26,885 次计划前向，单卡约 1 小时以内），GPU 启动脚本只用 `bash -n` 检查过，没有运行。是否在新的覆盖规则下重新预检，由用户决定。

### 1.1 On-policy 状态

- **轨迹**：`eval_outputs/mist_w3po_v1/decode/dev_v8_ctx0_guard_finalpost_s8`。v8，最终读因果 P，3,050 个 dev 在线窗口，就是 v2′ S1′ 用的解码。势函数也用 v8 打分（`P.V8` 的 merged Thinker）。训练会从 v8 出发，与 C0、C0-fp、v2′ 相同。
- **状态**：s = (w, 读 i, 读 i 的提交块末尾, y(s))。y(s) 是读 0..i 各自 `tok(read_log.new)` 的拼接。解码器每读提交的就是该读解码出的 ids，所有窗口的 `ctx` 都是空的（`--context 0`）。
- **参考条目**：应写窗口为 w 的打分器已评分句子（与 w 时间重叠最多，`diag_order_attr.due_of`，同 S1），按 v8 标签配方切块（`build_sched_windows.v8_chunks`，滞后 1 s，slot 取会议级 lowlat 映射）。块的应写读 ρ_lab 是第一个 t ≥ commit_ms 的读。
- **覆盖**：§14.2 的规则 (a)、(b)、(c)。
  - 候选段是 w 中 write_ms ≤ t_i 的已闭合段，加上同一会议开始更早的窗口的全部段。
  - (c) 只用于 > 1 s 的句子，并要求共享词型 ≥ 较小词集的一半。
  - 句子被覆盖时，它的所有块都算覆盖。
- **待写**：pending(s) 是未覆盖、且 ρ_lab ≤ i 的块（本读到期或已过期）。

### 1.2 O1 覆盖精确性（CPU）

任何一条断言失败，或者抽查一致率 < 0.95 → **停止**。

- **(i) 轨迹重建**：对每个 dev 窗口的每一读断言：
  - 各读 ids 解码回 `read_log.new`；
  - 拼接后解码等于 `raw`；
  - `ctx == ""`；
  - 用 `engine.Parser` 逐读喂入（write_ms = t），再按 `online_decode` 的方式关闭，复现存储的 `segments` 和 `blocks`（逐字段相同）。
  - 这样，每一读的 prompt 中 committed 段与解码器一致，到文本和解析状态这一层。
  - 文本相同但 id 切分不同（非规范分词）在 CPU 上无法排除，所以 O2 在 GPU 上另做贪心重放：teacher forcing 下，读块每个位置的 argmax 是否等于重建的 id。只报告，不作判定。
- **(ii)**：规则 (b) 用全部段时，对每一个 dev 已评分句子都等于打分器的 recalled()（断言）。
- **(iii) 263 个漏译单元**（`serial_v2p_precheck/s1/s1_rows_primary_finalpost.jsonl`）。断言：
  - (b)、(c) 从不成立（未召回，且 ≤1 s）；
  - 应写窗口等于 S1 的窗口；该单元最后一块的 ρ_lab 等于 S1 的应写读；
  - 覆盖函数复现它决定的每个 S1 / S1′ 字段：u 在应写读、下一读、更晚的读、别的窗口是否被写出，以及应写读和下一读上"别的段"的数目，从而 `why` 和 `why2` 两个分类逐个相同；
  - 每一读的覆盖状态与"w 内已写的匹配段或更早窗口的匹配段"一致。
  - 另报告：CHAIN 单元中被更早窗口覆盖的个数，以及在应写读之前就被覆盖的个数。
- **(iv) 人工抽查**：
  - 从 O2 人群中按 `SEED + 1` 随机抽 50 个状态，写入 `o1/review_states.md`。每个状态列出：本读之前到期的每个参考句子（文本、说话人、时间、判定和所用规则），以及模型到此为止写出的段（hyp slot、映射说话人、时间、写出读、文本）。
  - 我逐条判断每个判定是否正确。标准：模型输出里（任何标签）是否已有这句话的译文；长句译出主要内容即算覆盖；只有词面巧合、实际是别的话，不算覆盖。
  - 判断写入 `o1/review_judgments.jsonl`。
  - **一致率 = 正确判定数 / 判定总数。< 0.95 → 停止。** 同时报告"所有判定都正确"的状态占比。

### 1.3 O3 残差格精确性（CPU）

不通过 → 先修代码，不上 GPU。

- **对拍**：前向结果与暴力枚举一致，容差 1e-9。暴力枚举与格无关：枚举 ρ 赋值 × 每读顺序，历史和顺序都从赋值直接构造，y(s) 作为前缀。比较的量：
  - log Z（τ = 0.5 和 1；全部读打分，以及跳过无选择读后加回常数）；
  - 每条路径的分数和质量；
  - 残差读 0 的动作边际 q(a)；
  - 状态边际、推迟边际、顺序边际、路径数。
- **实例**：
  - 600 个随机合成残差实例（种子 20261110 起）；
  - 最多 300 个真实 O2 状态（块数 ≤ 12，有过期块的优先，路径 ≤ 40 万），用假 log 概率（整个前缀的确定性函数）。
  - 合成和真实实例中都必须有"残差读 0 有真顺序选择"的实例。
- **反例（必须全部抓到）**：
  - N1：在残差读 0 用 v2′ 原来的顺序规则（不把过期块算作携带），用于读 0 有真选择的实例；
  - N2：格的历史里去掉 y(s)，用于 y(s) 非空的实例。

### 1.4 O2 oracle 分歧（GPU）

- **人群**：同时满足：
  - 非最终读的读末；
  - 该读没有被 loop guard 或 budget 截断（read_log 无 `guard`）；
  - 结构状态（y(s) 停在段边界）；
  - pending(s) 非空。
- **量**：
  - q(wait|s)：§14.4 的残差格精确后验，τ = 0.5，联合退火；
  - p(wait|s)：v8 在 s 处的完整 softmax 中 `<wait>` 的概率（不屏蔽；s 在非最终读）。
- **D** = q(wait|s) < 0.5 且 p(wait|s) ≥ 0.5 的状态占比，即 oracle 要求写待写条目、模型却在等。**D < 0.05 → 停止。**
- **预算**：
  - 每个状态的计划前向数超过 3,000 的，排除并计数。
  - 其余状态的计划前向总数 ≤ 120,000 时全部打分。否则按 `SEED` 随机排列，取前缀直到达到 120,000，D 在这个均匀样本上计算。
  - 另外，所有有漏译单元待写的状态一律打分，D_263 在这些状态上计算。
- **打分协议**：
  - 引擎路径同 v2：`Engine.from_merged`、`audio_embeds`、`Prompter.ids`、左填充 + mask；
  - 非最终读 P 截在 t − 1.04 s；
  - 残差格的最终读用该窗口真实 `close_detect_ms` 的 `final_cut_ms`（`full=True`），屏蔽 `<wait>`，以 `<eos>` 结束，与解码时相同；
  - 无选择的读不打分（后验不变）。
- **只报告**：
  - KL(q‖p̄) 的均值和中位数，p̄ 是 p_v8 在 {wait, eos, spk1..8} 上重新归一化；
  - D_263；
  - CHAIN（68 个）和 NOTHING_ELSE_WRITTEN_AT_NEXT（41 个）单元中，在待写期间至少有一个分歧状态的个数；
  - q、p 的分布；有 / 无过期块的子组；
  - 贪心重放：读块逐 token、以及 s 处 argmax 是否为 `<wait>`；
  - 前向数、时间、显存。
- **运行检查（不是判定规则）**：
  - ψ 全部有限；
  - Σ_a q(a|s) = 1；
  - 冒烟：一张卡上跑 4 个状态，通过后才分片。

**GO 当且仅当 O1 和 O3 通过，且 D ≥ 0.05。** 每项一个设置，不扫参数。

### 2.2 O1 (i)–(iii) 自动断言：通过

- **(i) 轨迹重建**：3,050 个窗口、21,988 次读，全部断言通过：逐读解码、拼接等于 `raw`、`ctx` 为空、Parser 重放复现 `segments` 和 `blocks`。另外：
  - 17 次读被 loop guard / budget 截断；
  - 18 次读停在段内；
  - 窗口时长与轨迹的最终读时刻一致：3,050 / 3,050。
- **(ii)**：规则 (b) 用全部段时 = recalled()，8,340 / 8,340 个已评分句子。
- **(iii) 263 个漏译单元**：全部断言通过。CHAIN 68 个，其中：
  - 66 个从应写读起在 w 中一直未覆盖；
  - 1 个被更早的窗口写出（与 S1′ 的 "u 在别的窗口写出" 一致）；
  - 1 个在应写读**之前**就在 w 中写出过，然后被推迟又丢掉。
  - 其他类在应写读之前已覆盖的：DEFERRAL 4、DUE_FINAL 1、U_WRITTEN_AT_DUE 1、NOTHING_ELSE_WRITTEN_AT_DUE 1。
- **断言修正（如实记录）**：第一次运行在一条**我自己写的**断言上失败。那条断言要求 "CHAIN ⇒ 从应写读起一直未覆盖"，但 S1′ 的 CHAIN 只约束应写读、下一读和更晚的读，不约束更早的读，所以与预登记的 "复现 S1 / S1′ 字段" 不一致。改为 "w 中应写读及以后没有匹配段"，即 S1′ 本身的定义，并把 "应写读之前已覆盖" 单独计数。没有改动任何覆盖规则或判定常数。

| 规则判定 | 判定数 | 我判为错 | 错误类型 |

| 已覆盖 | 113 | 9 | 打分器按时间记分，但内容没写（垃圾输出、别句的重复）；或只写了不到一半 |

## 3. 如果要继续（需重新预登记，未执行）

覆盖判定需要不依赖打分器单元分配的规则，可能的改法：
- 短单元的文本规则改为允许同义回应类（yeah / yes / yep / okay / right 互认），并且不再用"同说话人另一句含相同词"来解释掉一个时间上恰好对齐的段；
- 用段与句子的时间对齐（各自的源区间 IoU）代替打分器的 best-overlap 分配；
- 长句用内容相似度（例如 chrF）代替纯时间记分，以排除垃圾输出和重复。

改完后应重新抽查（新种子），过线后再跑 O2。O2 的状态文件和脚本可以直接复用。
