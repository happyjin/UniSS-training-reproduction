## 0. 结论

| 项 | 结果 |
|---|---|

## 3. §2 变体预检（不含模型 `<wait>` 先验；**这是 §2 的变体，不是一′**）

**定义**（协调者要求，`crf_novel_ideas.zh-CN.md` §2.2、§10.3 "不含模型 `<wait>` 先验的版本"）：用同一批保存的 log 概率，令 end_lp ≡ 0，后验只由 token 的 log 概率和延迟决定；λ\* 二分到同一个 L_ref；C1/C2/C3 规则不变。没有新的 GPU 打分。

与 §2 原文的差别（需要写明）：
- token 的上下文是一′ 的打分方式（完整 S 前缀，含控制 token 和其他说话人的块），不是 §2 那样按说话人分流、省略控制 token；
- S 的串行化顺序固定；
- chunk 模式的候选边界 = 块边界（没有词对齐），最接近 §2 的 $\mathcal B_k$；any 模式允许在任意 token 处切块（包括说话人 token 与时间 token 之间、词中间），比 §2 更宽，v8 也从没见过这种切法；
- 没有 g、κ；最终读的 token 概率仍是屏蔽 `<wait>` 后的分布。

**块统计（训练）**

|---|---|---|---|---|---|

**解读**
- 去掉 `<wait>` 先验后，调度确实会变，但两种模式的问题不同：
  - any 模式：没有结束符代价时，后验大量在块中间切开（FFBS 平均块长从 12.4 降到 7.1 个 token，一半块 ≤ 2 词），平均 token 延迟受约束等于 L_ref，但块的完成时间反而**推迟**约 0.5 s（前半块提前、后半块推后）。这就是 §2 原设计要加 g 的原因；没有 g 时不可用。
  - chunk 模式：不碎片化；约 11% 的单元换了提交读，块偏移接近 0。λ\* > 0：没有 `<wait>` 先验时，"晚提交 → 听到更多 → token 概率更高"，后验偏晚，要靠延迟惩罚拉回。C1 只比阈值高 0.8 个百分点，而 v8 的打分本身有批组成噪声（`sched_crf_train_code.zh-CN.md` §5(v)：同一读 token 平均差 0.08 nats），这个"继续"是勉强的。
- C2 在两种模式下都是**推后**而不是提前，没有 S0 风险。
- 这只是预检规则上的结果。是否把 §2 变体作为新方法立项（需要 g、需要重新预登记），由用户决定。

## 4. 短单元诊断（`crf/diag_short_units.py`）

**问题**：v8 漏掉短单元，是"能译但不在这时开头"（时机/决策），还是"给了完整音频也译不出"（内容）？

**定义**（单元 = 参考话语，同 C1）
- ov50：其他说话人的单元（取并集）覆盖它至少 50%。
- (a) `p_content_final`：最终读（完整窗口音频、金标前缀）上，该单元**文本 token** 的平均 log 概率取 exp（几何平均概率）。
- (b) `p_open_final`：该单元在 S 中的开头 token（第一个块的说话人 token）在最终读上的概率；`p_open_max`：它在所有可达读上的最大值；`p_end_at_open`：同一位置上结束符的概率（最终读为 `<eos>`，其他读为 `<wait>`）。
- (c) `P_early`：后验中该单元（最后一个 token）在最终读之前提交的概率，λ = 0 与 λ\*（dev 也用训练的 λ\*）。
- (d) `_heur`：(a)、(b) 在启发式提交读上的值。
- 表中为 中位数 [四分位]，以及 < 0.3、< 0.5 的占比。

**注意**：训练窗口是 v8 学过的目标，内容能力被高估；dev 窗口没有训练过，更可信。

### 4.3 解读

1. **不是时机问题。** 启发式在最终读之前提交的短单元，后验以 0.97–1.00 的概率同样提前提交；在开头位置上，启发式读处 p(`<wait>`) 的中位数是 0.00（上四分位 0.02），最终读处 p(`<eos>`) ≈ 0。也就是说，模型在该开头的时刻**想写东西**，也不认为窗口已经结束。
2. **孤立短单元也不是内容问题。** 一旦开头，孤立 ≤1 s 单元的文本 token 几何平均概率中位数为 0.87（训练）/ 0.89（dev），≤0.5 s 为 0.90 / 0.92，比长单元高（长单元 0.27–0.28，词多、信息量大）。
3. **问题集中在开头 token。** 短单元的金标说话人 token 在最终读上只有 0.37（训练）/ 0.50（dev），≤0.5 s 只有 0.27 / 0.28；长单元是 0.96。由于此处 `<wait>` 被屏蔽、p(`<eos>`) ≈ 0，而结束时间 token 之后语法上只能接说话人 token，剩下的概率质量只能落在**别的说话人 token** 上：要么把这个短单元归给了别的说话人，要么想先开另一段（顺序不同）。可达读上的最大值（0.50 / 0.72）也没有好多少，所以不是"等一等就会开"。
4. **重叠短单元另有内容问题。** dev 上重叠 ≤1 s 单元的内容中位数 0.43，42% 低于 0.3；孤立的只有 13%。这部分是声学感知不足（重叠语音），与 §12 的结论一致。
5. **限制**：只保存了金标 token 和结束符的 log 概率，所以不能直接区分"归属错"和"顺序不同"。这是教师强制、金标前缀下的诊断；自由解码时前缀已经偏离，漏译还会叠加暴露偏差。区分的办法很便宜：在开头位置额外存下所有说话人 token 的概率（8 卡约 10 min），用户同意后可做。
6. **对方法的含义**：一′ 和 §2 都固定了 S（固定说话人 token 和顺序），只决定"何时提交"，不触及"开谁"。如果瓶颈是顺序，一′-b（顺序作为隐变量）才对口；如果是归属，就属于说话人输入或输出侧的归属问题。

## 7. 补充：开头位置重新打分——归属还是顺序（2026-11-09 18:20–18:30 UTC）

**问题**：§4.3 发现，短单元的金标开头 token（它的说话人 token）概率低，而概率质量落在别的说话人 token 上。两种解释：
- **归属（ATTRIBUTION）**：模型想把这句插话说在错误的说话人名下，或并进上一位说话人；
- **顺序（ORDER）**：模型想先输出另一位说话人尚未提交的段，即串行化顺序不同。

**代码**：`experiments/mist_w3po_v1/crf/rescore_openers.py`（测试 `crf/test_rescore_openers.py`）。决策规则在看任何结果之前写进脚本并提交（`6e3c98d2`），GPU 运行在其后。

**做法**（预检样本中全部 ≤1 s 单元：训练 393 个、dev 213 个；dev 是主要证据，v8 没有训练过）
- 位置：每个单元的金标开头位置（前缀 = 金标 S[:j0]），分别在**最终读**和**启发式提交读**上测（两者相同时只算一次）。最终读照解码方式屏蔽 `<wait>`。
- 第 1 遍：在开头位置取完整的下一 token 分布，归并成类（8 个说话人 token 各自一类、`<wait>`、`<eos>`、时间 token、文本 token = 其余），记录 argmax 和各类概率质量；同时记录 lpG = 金标首块在金标说话人 token 之后各 token 的平均 log 概率。
- 第 2 遍：k′ = 除金标外概率最大的说话人（argmax 是错误说话人时就是 argmax）。
  - 强制续写 1：把金标开头换成 `<spk_k′>`，对插话首块的其余 token（开始时间、文本、结束时间）打分，取平均 log 概率 lpA。高 → 归属。
  - 强制续写 2：k′ 在 S 中 j0 之后第一个尚未提交的块，接在 `<spk_k′>` 之后打分，取 lpB。高 → 顺序。
  - 记录 k′ 是否就是 S 中紧挨着的上一段的说话人（并进上一位）。
- **预先写定的规则**：argmax 为金标说话人 → GOLD；argmax 为错误说话人 k′ 时，k′ 后面没有待提交的块 → ATTRIBUTION_NOPENDING（算作归属），否则 lpA − lpB ≥ 0.5 nats → ATTRIBUTION，≤ −0.5 → ORDER，其余 → AMBIGUOUS；argmax 为时间或文本 token → OTHER_CONT；`<eos>` 或 `<wait>` → END_WAIT。

**运行**：8 卡，每卡先训练分片再 dev 分片，60 s 错开，setsid；每进程峰值 69,258 MiB，每卡合计峰值 106.6–111.8 GiB；看门狗未触发；18:20:30 启动，18:29:30 全部结束，卡上已无我的进程。先在卡 7 上用 6 个 dev 条目做过一次冒烟（输出在 work 目录）。

### 7.3 结论

1. **开头位置几乎所有概率都在说话人 token 上**：`<wait>`、`<eos>`、时间、文本 token 的质量中位数都是 0.00，OTHER_CONT 为 0%。所以问题确实是"选哪个说话人 token"。
2. **孤立短单元 → 归属。** dev 最终读上 30% 归属、0% 顺序；≤0.5 s 时 60% 归属。绝大多数是错误说话人 k′ 在窗口后面根本没有段（27% / 53%），而且同一句内容挂在 k′ 名下和挂在金标名下概率相同（lpA − lpG 中位数 0.00）。也就是说，v8 能译出这句插话，只是说话人标签选错了，基本不是并进上一位（k′ = 上一段说话人 0%）。
3. **重叠短单元 → 顺序为主。** dev 最终读上 43% 顺序、13% 归属；≤0.5 s 时 61% 顺序。错误说话人 k′ 的待提交段在 `<spk_k′>` 之后的概率（lpB −1.58）远高于把插话挂在 k′ 名下（lpA −4.19）。另有 23% 的错误 argmax 是上一段的说话人。
4. **顺序问题主要出现在最终读。** 在启发式提交读上，重叠短单元的 ORDER 从 43% 降到 14%，GOLD 从 40% 升到 61%。最终读时对方的长段已经说完、等着提交，模型想先写它；在插话本该提交的时刻，对方的段还没说完，模型愿意先写插话。
5. **对方法的含义**：
   - 重叠插话的问题是顺序，正是一′-b（交错顺序作为隐变量）的目标；一′ 和 §2 都固定了 S，处理不了。
   - 孤立短插话的问题是说话人标签，内容和时机都没问题。它不在调度方法的范围内，属于说话人归属（diarizer 输入或输出侧的说话人选择）。
6. **限制**：规则中 lpA 与 lpG 几乎总是相等（说话人 token 之后的内容基本不受说话人条件影响），所以 A − B 的比较主要由 lpB（k′ 待提交段此刻是否可写）决定。"无待提交段"一类在规则上记为归属，但这也包含"想开一个不存在的段"的情况。数据只来自教师强制和金标前缀；dev 的组内样本量为 38–113。
