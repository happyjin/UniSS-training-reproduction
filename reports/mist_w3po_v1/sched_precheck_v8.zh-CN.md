## 3. §2 变体预检（不含模型 `<wait>` 先验；**这是 §2 的变体，不是一′**）

**定义**（协调者要求，`crf_novel_ideas.zh-CN.md` §2.2、§10.3 "不含模型 `<wait>` 先验的版本"）：用同一批保存的 log 概率，令 end_lp ≡ 0，后验只由 token 的 log 概率和延迟决定；λ\* 二分到同一个 L_ref；C1/C2/C3 规则不变。没有新的 GPU 打分。

与 §2 原文的差别（需要写明）：
- token 的上下文是一′ 的打分方式（完整 S 前缀，含控制 token 和其他说话人的块），不是 §2 那样按说话人分流、省略控制 token；
- S 的串行化顺序固定；
- chunk 模式的候选边界 = 块边界（没有词对齐），最接近 §2 的 $\mathcal B_k$；any 模式允许在任意 token 处切块（包括说话人 token 与时间 token 之间、词中间），比 §2 更宽，v8 也从没见过这种切法；
- 没有 g、κ；最终读的 token 概率仍是屏蔽 `<wait>` 后的分布。

**解读**
- 去掉 `<wait>` 先验后，调度确实会变，但两种模式的问题不同：
  - any 模式：没有结束符代价时，后验大量在块中间切开（FFBS 平均块长从 12.4 降到 7.1 个 token，一半块 ≤ 2 词），平均 token 延迟受约束等于 L_ref，但块的完成时间反而**推迟**约 0.5 s（前半块提前、后半块推后）。这就是 §2 原设计要加 g 的原因；没有 g 时不可用。
  - chunk 模式：不碎片化；约 11% 的单元换了提交读，块偏移接近 0。λ\* > 0：没有 `<wait>` 先验时，"晚提交 → 听到更多 → token 概率更高"，后验偏晚，要靠延迟惩罚拉回。C1 只比阈值高 0.8 个百分点，而 v8 的打分本身有批组成噪声（`sched_crf_train_code.zh-CN.md` §5(v)：同一读 token 平均差 0.08 nats），这个"继续"是勉强的。
- C2 在两种模式下都是**推后**而不是提前，没有 S0 风险。
- 这只是预检规则上的结果。是否把 §2 变体作为新方法立项（需要 g、需要重新预登记），由用户决定。

## 4. 短单元诊断（`crf/diag_short_units.py`）

**问题**：v8 漏掉短单元，是"能译但不在这时开头"（时机/决策），还是"给了完整音频也译不出"（内容）？

**定义**（单元 = 参考话语，同 C1）
- ov50：其他说话人的单元（取并集）覆盖它至少 50%。
- (a) `p_content_final`：最终读（完整窗口音频、金标前缀）上，该单元**文本 token** 的平均 log 概率取 exp（几何平均概率）。
- (b) `p_open_final`：该单元在 S 中的开头 token（第一个块的说话人 token）在最终读上的概率；`p_open_max`：它在所有可达读上的最大值；`p_end_at_open`：同一位置上结束符的概率（最终读为 `<eos>`，其他读为 `<wait>`）。
- (c) `P_early`：后验中该单元（最后一个 token）在最终读之前提交的概率，λ = 0 与 λ\*（dev 也用训练的 λ\*）。
- (d) `_heur`：(a)、(b) 在启发式提交读上的值。
- 表中为 中位数 [四分位]，以及 < 0.3、< 0.5 的占比。

**注意**：训练窗口是 v8 学过的目标，内容能力被高估；dev 窗口没有训练过，更可信。

### 4.3 解读

1. **不是时机问题。** 启发式在最终读之前提交的短单元，后验以 0.97–1.00 的概率同样提前提交；在开头位置上，启发式读处 p(`<wait>`) 的中位数是 0.00（上四分位 0.02），最终读处 p(`<eos>`) ≈ 0。也就是说，模型在该开头的时刻**想写东西**，也不认为窗口已经结束。
2. **孤立短单元也不是内容问题。** 一旦开头，孤立 ≤1 s 单元的文本 token 几何平均概率中位数为 0.87（训练）/ 0.89（dev），≤0.5 s 为 0.90 / 0.92，比长单元高（长单元 0.27–0.28，词多、信息量大）。
3. **问题集中在开头 token。** 短单元的金标说话人 token 在最终读上只有 0.37（训练）/ 0.50（dev），≤0.5 s 只有 0.27 / 0.28；长单元是 0.96。由于此处 `<wait>` 被屏蔽、p(`<eos>`) ≈ 0，而结束时间 token 之后语法上只能接说话人 token，剩下的概率质量只能落在**别的说话人 token** 上：要么把这个短单元归给了别的说话人，要么想先开另一段（顺序不同）。可达读上的最大值（0.50 / 0.72）也没有好多少，所以不是"等一等就会开"。
4. **重叠短单元另有内容问题。** dev 上重叠 ≤1 s 单元的内容中位数 0.43，42% 低于 0.3；孤立的只有 13%。这部分是声学感知不足（重叠语音），与 §12 的结论一致。
5. **限制**：只保存了金标 token 和结束符的 log 概率，所以不能直接区分"归属错"和"顺序不同"。这是教师强制、金标前缀下的诊断；自由解码时前缀已经偏离，漏译还会叠加暴露偏差。区分的办法很便宜：在开头位置额外存下所有说话人 token 的概率（8 卡约 10 min），用户同意后可做。
6. **对方法的含义**：一′ 和 §2 都固定了 S（固定说话人 token 和顺序），只决定"何时提交"，不触及"开谁"。如果瓶颈是顺序，一′-b（顺序作为隐变量）才对口；如果是归属，就属于说话人输入或输出侧的归属问题。

## 7. 补充：开头位置重新打分——归属还是顺序（2026-11-09 18:20–18:30 UTC）

**问题**：§4.3 发现，短单元的金标开头 token（它的说话人 token）概率低，而概率质量落在别的说话人 token 上。两种解释：
- **归属（ATTRIBUTION）**：模型想把这句插话说在错误的说话人名下，或并进上一位说话人；
- **顺序（ORDER）**：模型想先输出另一位说话人尚未提交的段，即串行化顺序不同。

**代码**：`experiments/mist_w3po_v1/crf/rescore_openers.py`（测试 `crf/test_rescore_openers.py`）。决策规则在看任何结果之前写进脚本并提交（`6e3c98d2`），GPU 运行在其后。

**做法**（预检样本中全部 ≤1 s 单元：训练 393 个、dev 213 个；dev 是主要证据，v8 没有训练过）
- 位置：每个单元的金标开头位置（前缀 = 金标 S[:j0]），分别在**最终读**和**启发式提交读**上测（两者相同时只算一次）。最终读照解码方式屏蔽 `<wait>`。
- 第 1 遍：在开头位置取完整的下一 token 分布，归并成类（8 个说话人 token 各自一类、`<wait>`、`<eos>`、时间 token、文本 token = 其余），记录 argmax 和各类概率质量；同时记录 lpG = 金标首块在金标说话人 token 之后各 token 的平均 log 概率。
- 第 2 遍：k′ = 除金标外概率最大的说话人（argmax 是错误说话人时就是 argmax）。
  - 强制续写 1：把金标开头换成 `<spk_k′>`，对插话首块的其余 token（开始时间、文本、结束时间）打分，取平均 log 概率 lpA。高 → 归属。

  - 记录 k′ 是否就是 S 中紧挨着的上一段的说话人（并进上一位）。
- **预先写定的规则**：argmax 为金标说话人 → GOLD；argmax 为错误说话人 k′ 时，k′ 后面没有待提交的块 → ATTRIBUTION_NOPENDING（算作归属），否则 lpA − lpB ≥ 0.5 nats → ATTRIBUTION，≤ −0.5 → ORDER，其余 → AMBIGUOUS；argmax 为时间或文本 token → OTHER_CONT；`<eos>` 或 `<wait>` → END_WAIT。

### 7.3 结论

1. **开头位置几乎所有概率都在说话人 token 上**：`<wait>`、`<eos>`、时间、文本 token 的质量中位数都是 0.00，OTHER_CONT 为 0%。所以问题确实是"选哪个说话人 token"。
2. **孤立短单元 → 归属。** dev 最终读上 30% 归属、0% 顺序；≤0.5 s 时 60% 归属。绝大多数是错误说话人 k′ 在窗口后面根本没有段（27% / 53%），而且同一句内容挂在 k′ 名下和挂在金标名下概率相同（lpA − lpG 中位数 0.00）。也就是说，v8 能译出这句插话，只是说话人标签选错了，基本不是并进上一位（k′ = 上一段说话人 0%）。
3. **重叠短单元 → 顺序为主。** dev 最终读上 43% 顺序、13% 归属；≤0.5 s 时 61% 顺序。错误说话人 k′ 的待提交段在 `<spk_k′>` 之后的概率（lpB −1.58）远高于把插话挂在 k′ 名下（lpA −4.19）。另有 23% 的错误 argmax 是上一段的说话人。
4. **顺序问题主要出现在最终读。** 在启发式提交读上，重叠短单元的 ORDER 从 43% 降到 14%，GOLD 从 40% 升到 61%。最终读时对方的长段已经说完、等着提交，模型想先写它；在插话本该提交的时刻，对方的段还没说完，模型愿意先写插话。
5. **对方法的含义**：
   - 重叠插话的问题是顺序，正是一′-b（交错顺序作为隐变量）的目标；一′ 和 §2 都固定了 S，处理不了。
   - 孤立短插话的问题是说话人标签，内容和时机都没问题。它不在调度方法的范围内，属于说话人归属（diarizer 输入或输出侧的说话人选择）。
6. **限制**：规则中 lpA 与 lpG 几乎总是相等（说话人 token 之后的内容基本不受说话人条件影响），所以 A − B 的比较主要由 lpB（k′ 待提交段此刻是否可写）决定。"无待提交段"一类在规则上记为归属，但这也包含"想开一个不存在的段"的情况。数据只来自教师强制和金标前缀；dev 的组内样本量为 38–113。

### 8.1 检查 A：v8 自己在线解码中的短单元漏译

**用的解码**：正式闸门的参考解码 `eval_outputs/mist_w3po_v1/decode/dev_v8_ctx0_guard_s8`（v8、ctx0、保护版协议、8 分片），dev 在线窗口 `windows_dev_online.jsonl`（15 个会议、3,050 个窗口）。

**匹配：直接复用评测代码，没有另写。** 原样运行 `reports/gstar_si_v8/overlap_score.score(online=True)`（即 `score_run.py` 用的打分器）。第一次调用 `recalled()` 时，从它的栈帧读出每个会议的状态：被打分的话语、unit_of、段到单元的分配 got、会议级说话人映射 mp，并当场对所有话语求 `recalled()`。漏译的定义是打分器自己判 `recalled = False`。复算出的 tcpBLEU、CR、短单元召回与 `score_text.json` **完全一致**（脚本内有断言）。

**定义**
- 单元：时长 ≤1 s 的被打分话语（与打分器的短单元召回同一集合）。孤立 / 重叠按 md 的 ov50 划分：其他说话人的被打分话语（取并集）覆盖它至少 50% 即为重叠。
- 应写读：取与该单元重叠最多的在线窗口，用 v8 标签规则：单元结束 + 1.0 s 之后的第一次读；没有这样的读就取窗口的最后一次读。提交时间一律用原始读时间，不用打分器按检测时间钳位后的值。
- 文本匹配（预先写定）：小写后只保留 `[a-z0-9']` 词，得到参考词序列 r。一个假设段算匹配，需要同时满足：
  - r 恰好是该段词序列的开头或结尾（整段就是这句插话，或插话粘在段首或段尾）；
  - 该段的源时间区间前后各放宽 2 s（打分器的 collar）后与单元重叠；
  - 不能被"该段所属说话人自己的参考里也有 r"解释掉。
- 分类按以下顺序取第一个成立的：
  - (ii) **错标**：匹配段的槽位经 mp 映射到别的说话人；
  - (iv) **自身未计入**：匹配段在本人槽位下，但没有被计到该单元；
  - (i) **顺序→漏译**：与该单元时间重叠的其他说话人，在应写读或之后，提交了被打分器计入其单元、源区间离本单元不超过 1 s 的段（即与本单元同时的那部分内容）；
  - (iii) **静默**：应写时间 ±2 s 内没有任何说话人提交过非空段；
  - (iv) **其他**：其余情况。

**细节**
- **孤立漏译多数发生在窗口最后一次读。** 435 个中有 342 个（79%）的应写读就是窗口的最后一次读；13 个所在位置根本没有在线窗口。
- **错标的匹配很干净。** 347 个错标中有 330 个是整段完全相同，例如 "Yeah." 写在了另一个说话人名下。
- **"其他"里大多也是错标，只是措辞不同（事后分析）。** 孤立"其他"128 个中有 99 个，在本单元位置（±0.2 s）有一个 ≤4 词的短段，写在别的说话人槽位下，而且不能用那个说话人自己同时在说的话解释。所以孤立短单元的漏译里，约 79% 实际是"写了，但写在了错误的说话人名下"（严格错标 56% + 这一部分 23%）。
- **重叠的顺序→漏译 151 个**：
  - 其中 112 个（74%）的对方同时段就是在应写读那一次提交的，中位时间差为 0；38 个（25%）的应写读是窗口的最后一次读。
  - 其中 45 个在本单元位置也有上述"别的槽位短段"，可能是措辞不同的错标。所以顺序→漏译占重叠漏译的比例在 **36%–51%** 之间。
- **静默几乎不存在**（全部只有 7 个）：短单元漏译时，附近总有东西被写出来。

### 8.2 检查 B：孤立短单元归属错误的原因

**样本**：§7 重新打分中，在**最终读**上被判为归属的条目（ATTRIBUTION + ATTRIBUTION_NOPENDING）。dev 为主，train 作参考；同组的 GOLD 条目作对照。

**定义**
- **提示中的 P**：窗口的 lowlat 后验，按引擎的做法把 t_r − 1.04 s 之后的帧置零（`Engine.audio_embeds`）。单元的帧为 [a/80 ms, ⌈b/80 ms⌉)。<|spk k|> 对应第 k−1 列。
- **证据**：
  - 单元帧里没有任何一列 ≥ 0.5，记为"无证据"。再细分：完整 P（不置零）里有 → UNSEEN（被前瞻掩码挡住）；完整 P 里也没有 → SILENT。
  - 否则看单元帧上 P 均值的 argmax，记为金标列 / k′ 列 / 其他列。
- **窗口级映射**：复用 `data/build_windows_zh2en.window_slot_map`（S0-5：只在窗口内按帧重叠做匈牙利匹配）。成员为参考窗口的话语，session 映射用 `slot_map.json` 的 lowlat。
- **原因划分（预先写定）**：
  - LABEL_NOISE：证据为 k′ 列，且窗口映射也把金标说话人映到 k′；
  - WRONG_EVIDENCE：证据为 k′ 列，但窗口映射不是 k′；
  - NO_EVIDENCE：无证据；
  - IGNORES_EVIDENCE：证据为金标列；
  - OTHER_EVIDENCE：证据为其他列。

| 组（最终读） | n | **无证据**（UNSEEN / SILENT） | 标签噪声 | 跟随错误证据 | 无视正确证据 | 其他列 |
|---|---|---|---|---|---|---|
| **dev ≤1 s 孤立，归属** | 33 | **31（94%）**（30 / 1） | 1（3%） | 0 | 1（3%） | 0 |
| dev ≤0.5 s 孤立，归属 | 26 | 24（92%）（24 / 0） | 1 | 0 | 1 | 0 |
| dev ≤1 s 孤立，GOLD（对照） | 77 | 19（25%） | 0 | 0 | 56（73%） | 2 |
| dev ≤1 s 重叠，归属（参考） | 13 | 4（31%） | 0 | 3（23%） | 4（31%） | 2（15%） |
| train ≤1 s 孤立，归属 | 79 | 70（89%）（67 / 3） | 5（6%） | 3（4%） | 1（1%） | 0 |
| train ≤1 s 孤立，GOLD（对照） | 141 | 51（36%） | 0 | 1 | 87（62%） | 2 |
| train ≤1 s 重叠，归属（参考） | 29 | 9（31%） | 1 | 8（28%） | 6（21%） | 5（17%） |

**dev 孤立归属（33 个）的细节**
- 提示 P 在单元帧上的均值，金标列 / k′ 列：中位数 0.00 / 0.00，均值 0.029 / 0.015。可见帧比例的中位数为 0，**28 个完全不可见**。
- 完整 P（不置零）：金标列 / k′ 列中位数 0.67 / 0.01；argmax 为金标列 29 个（**88%**），k′ 列 2 个。
- 所在窗口很短：时长中位数 1.19 s（GOLD 对照为 2.98 s），单元结束到窗口结束中位数 0.5 s；27 个窗口只有一位说话人。
- 窗口级映射与会议级一致 29 个，映到 k′ 1 个，映到其他 3 个。所以标签噪声最多 4/33（12%）；对照组为 4/77（5%）。train 上映到 k′ 的有 7/79（9%）。
- 条件比例（dev 孤立，归属 + GOLD）：无证据时归属错误 31/50 = **62%**；有证据时 2/60 = **3%**。train 上为 70/121 = 58% 对 9/99 = 9%。

### 8.3 事后核对：在线解码里是同一个机制吗？

在 `dev_v8_ctx0_guard_s8` 上，对孤立 ≤1 s 话语，在决定其说话人的那次读上看提示 P。决定读的取法：已召回的取第一个召回段的提交读，错标的取错标段的提交读。期望槽位 = mp 映射到该说话人的槽位。

| 组 | n | 提示 P 无证据 | 证据指向写出的错误槽位 | 证据指向正确槽位 | 在窗口最后一次读决定 | 窗口时长中位数 |
|---|---|---|---|---|---|---|
| 错标 | 236 | **204（86%）**，其中 194 个完全不可见 | 24（10%） | 4（2%） | 204（86%） | **1.14 s** |
| 已召回 | 905 | 257（28%） | — | 628（69%） | 317（35%） | 6.58 s |

- 无证据时错标率 204/461 = **44%**；正确证据可见时 4/632 = **0.6%**。
- 错标单元的完整 P 有 73% 指向正确槽位。

### 8.4 结论

1. **重叠短单元：顺序确实造成了一部分真实漏译，但不是全部。** 重叠短单元的漏译中：
   - 36%–51% 是对方的同时段在应写读或之后被写出、插话再也没写（其中 74% 在同一次读）；
   - 35% 是错标。
   
   两段在同一次读里到期时漏译率高约 10 个百分点；而在已召回的重叠短单元中，对方先写也占约一半。所以要解决的是"同一读内的竞争、写了对方就不再回头写插话"，不是"先后顺序"本身。这支持 §7 的一′-b 方向（读内顺序作为隐变量），但只覆盖重叠漏译的一半左右。
2. **孤立短单元：漏译的主体是错标，原因是说话人证据被掩码，既不是标签噪声，也不是 diarizer 判错。**
   - 在线解码中，孤立短单元漏译约 79% 是写在了错误的说话人名下。
   - 重新打分判为归属的条目中，94%（dev）/ 89%（train）在提示里**看不到这句插话的 diarizer 帧**：最终读把最后 1.04 s 的 P 置零，而这些插话所在的窗口大约只有 1.2 s，且在窗口结束前约 0.5 s 才说完。
   - 完整 P 有 88% 指向正确的列；窗口级映射与会议级不一致的最多 12%。
   - 模型看不到证据时只能猜，错误率 62%（在线 44%）；看得到证据时只有 3%（在线 0.6%）。
3. **对方法的含义（只是线索，未做任何改动）**：
   - 在线协议中，窗口最后一次读的提交时间会被钳位到关闭检测时刻。93.6% 的 dev 在线窗口满足 close_detect − 1.04 s ≥ 窗口时长，即到那时整个窗口的 lowlat 后验都已确定。所以在最终读上提供 P 直到 min(时长, close_detect − 1.04 s) 是**因果的**，可以直接针对孤立插话的归属问题。
   - 但 v8 的训练行对最终读也做了同样的掩码（`build_ami_gstar_stream_rows_zh2en.py`：每次读 post_until = t − 1040），v8 从没见过未掩码的最终读。所以需要先做纯测试端的检查，或者用新的 SFT 行，并且按规定必须通过 ASR-BLEU 闸门。是否做由用户决定。

### 8.5 注意事项

- **只有一次解码。** 不同分片之间，保护版 dev 的 ov 约有 ±0.3 的波动；短单元计数的抽样噪声没有做 bootstrap。
- **严格文本匹配让"错标"成为下界。** 措辞不同的错标会落到"其他"或"顺序→漏译"里，8.1 用"本单元位置的别的槽位短段"给了一个范围。backchannel 词表的宽松版本只作敏感性检查，未计入表中。
- **(i) 的定义较宽。** 对方话语通常比插话长、结束得晚，只要对方同时段被写出，"在应写读或之后提交"几乎自动成立。所以 (i) 只说明"与顺序竞争相符"；更接近因果的证据是 8.1(c) 中同一读竞争时漏译率更高。
- **检查 B 用的是教师强制、金标前缀的条目**，窗口是参考窗口（训练格式），不是在线窗口；dev 组内只有 26–33 个。8.3 在在线解码上复现了同一机制，但它是看到检查 B 之后才加的事后分析。
- **两种"正确槽位"的参照不同。** 在线解码用打分器按文本做的映射 mp；检查 B 用会议级 lowlat 映射（`slot_map.json`），它与在线窗口所用的后验（zh_mix_v8、nemotron_lowlat_zh8）来源不同。
- 应写读用的是 v8 的标签规则（结束 + 1 s 之后的下一次读），时间是原始读时间，不是打分器按检测时间钳位后的时间。
