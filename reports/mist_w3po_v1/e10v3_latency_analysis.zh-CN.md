# LiveInterpret v3 为什么延迟比 baseline B 大、大段等待多：原因分析与解决方案

写于 2026-11-28（布拉格时间）。

**数据来源：** 只用现有输出，没有新跑模型。
- v3：`e10_multispk/output/demo_game_v3/raw_*` 的逐窗口解码（写出时刻 `write_ms`、文本、每段语音时长）。
- B：`eval_outputs/mist_w3po_v1/speech/game_b_*__t1c/talker_in/blocks.jsonl` 的逐窗口写出块。
- 两者都对应试听页上的时间线（页面 `tgt`）。
- 6 段电竞音频（gz01–03 中→英，ge01/02/04 英→中），共 133 个在线窗口，每个版本各解码一次（单 seed）。

**脚本：**
- `e10_multispk/analysis/v3_vs_b_window_latency.py`
- `e10_multispk/analysis/v3_vs_b_write_punct.py`

**口径说明：**
- **文本 LAAL** 是逐窗口算的：词的延迟取它所在写出步的 `write_ms`，|X| 取窗口时长，两个版本用同一个 γ（|Y| 取两者输出词数的较大值），然后对窗口取平均。
- 不计算计算耗时（NCA），和试听页的时间线一致。
- 电竞数据没有人工参考译文，所以没有算基于 ASR 时间戳的语音 LAAL。语音一侧用“排队延迟”和“静音段”来刻画。

|---|---|---|---|---|---|
| gz01 | 8 / 1 | 39 / 9 | 33 | 32 | 230 / 262 |
| gz02 | 11 / 2 | 65 / 7 | 63 | 52 | 205 / 263 |
| gz03 | 6 / 2 | 36 / 7 | 34 | 25 | 228 / 276 |
| ge01 | 2 / 0 | 7 / 0 | 7 | 5 | 268 / 280 |
| ge02 | 4 / 2 | 29 / 7 | 28 | 22 | 234 / 267 |
| ge04 | 5 / 1 | 28 / 4 | 24 | 22 | 244 / 287 |

- **v3 的长静音 85–97% 发生在原声正在说话的时候，并且大部分时间 B 正在出声。** 这些不是自然停顿，是模型还在等、没有写出。
- 播放规则是每个说话人一条队列，所以只要有任何写出，就会立刻出声。静音段因此等价于“这段时间没有写出”，或者对应的是报错窗口。
- **gz02 最严重的原因是窗口短**（均长 9.6 s）。首次写出前的等待加上窗口末尾的集中写出，占了窗口的大半。

## 3. 排除的原因

| 怀疑 | 数据 | 结论 |
|---|---|---|
| Talker 排队太长，把延迟拉大 | 排队延迟（s/词）v3 / B：0.68/1.17、0.60/1.29、1.02/3.21、1.27/1.32、1.07/1.22、1.06/1.44 | **v3 的排队反而比 B 短**，不是原因 |
| Talker 语速慢 | 每词语音时长 v3 / B：中→英 0.29 / 0.36 s，英→中 0.20–0.22 / 0.21–0.24 s | v3 说得更快。这让同样的内容占用更短的时间，所以静音比例会偏高一些，但不会造成等待 |
| 训练标签本身比 B 慢 | v3 的流式标签和 B 用同一条规则（标点块在最后一个源词后 1 s 提交），只是网格从 1 s 改成 640 ms，按规则平均反而早约 0.2 s | 标签不是原因 |
| 说话人 token 延迟 1040 ms | v3 和 B 一样，都只用到 t − 1040 ms 的后验 | 两者相同，不能解释差距 |
| 输出更短导致的假象 | 词数 v3 / B：975/1013、978/1066、1014/1437、1656/1807、1289/1381、1424/1703 | 文本 LAAL 用了统一的 γ，已经扣除了输出长度的影响；输出偏短只影响静音比例 |

## 4. 为什么 v3 的决策偏保守

部分是推断，标在每条后面。

1. **v3 的写出节奏基本照搬训练时的平均节奏，没有跟上电竞语速。**（有数据支持，机制为推断）
   - 训练用的 AMI 流式记录：中→英每 2.4 s 写一次、每次 6.5 个词；英→中每 2.0 s 写一次、每次 8.2 个词。
   - 在电竞上，v3 的写出间隔是 1.6–2.9 s，和训练时差不多。
   - B 在电竞上写得比它在 AMI 上更勤（1.4–1.9 s 一次）。电竞解说语速快，标点块完成得更快，一个按内容决定的策略理应写得更勤。
   - 这说明 v3 的“写”更多依赖“过了多久”这种先验，对“内容是否已经完整”判断不够自信。
2. **模型更小，听电竞音频没把握，贪心解码时就倾向于等。**（推断）
   - v3 是 Voxtral + 4B Thinker，B 是 Qwen3-Omni-30B-A3B。面对快语速、带背景音和多人抢话的电竞解说，v3 的 p(写) 往往到不了 0.5，贪心解码就一直选“等”，直到整句明确、或者窗口结束才写。
   - 旁证：LiveInterpret 团队自己的评测也给“写”设了概率阈值 0.3 / 0.2（`docs/S5_新旧同传对比_同样本.md` 中的 `thr03` / `thr02`）。这说明这类模型贪心解码时偏保守，是已知现象。
3. **类别不平衡更重。**（推断）
   - 640 ms 网格下，流式记录中“写”只占 27–32% 的步。
   - 另外，一半联合训练数据是离线和单说话人记录，它们的决策 loss 被屏蔽，所以决策监督只来自约 5.5 万条流式记录。
4. **训练窗口短，测试窗口长。**（推断）训练窗口平均 6.2 s，电竞窗口是 9.6–17.8 s。B 也是同样的训练窗口，但大模型的外推更稳。

## 5. 解决方案（按代价从小到大）

| # | 方案 | 改什么 | 代价 | 风险与验收 |
|---|---|---|---|---|
| **S1（建议先做）** | **写出阈值解码**：p(`<|W|>`) ≥ τ 就写，不再取 argmax | 只改推理（`run_e10.py` 加一个 `--write_threshold`） | 不训练。在 AMI dev（开源数据）上定 τ，目标是让 v3 的文本 LAAL 接近 B；然后在 6 段电竞上解码一次，4 张卡约半小时 | 写早了，上下文就少，可能降 BLEU 或增加复读（已有循环保护）。验收：AMI dev 和电竞的 BLEU 都不低于当前 v3，文本 LAAL 下降，>3 s 静音段减少。只取一个 τ（LI 团队用过 0.3），不扫参 |
| S2 | **决策 loss 按类别加权**：“写”类的权重乘 (1 − p)/p，约 2–2.7 | 重训联合阶段（从现有 O2 开始），数据、标签、训练部位与 B 保持一致 | 4 张卡约 1 小时，再解码半小时 | 只有 S1 不够时再做。可能过度写出，产生碎片化的短句。验收同上 |
| S3 | **语速扰动数据增强**：训练音频按 1.1–1.3 倍变速，标签时间同步缩放 | 重训 | 数据准备加训练约 2 小时 | 针对“写出节奏不随语速变”这个问题，但会和 B 的训练数据不一致，需要你确认 |
| S4 | **加长训练窗口**：拼接相邻的 AMI 窗口，构造 12–18 s 的记录 | 重训 | 同上 | 同样与 B 的数据不一致，需要你确认 |
| 不建议 | 改 Talker（放慢语速、改排队） | – | – | Talker 不是延迟的来源。放慢语速只能填一部分静音，还会进一步拉高语音 LAAL |

**建议：** 先做 S1，它不改训练，又和 LI 团队自己的做法一致。如果 S1 之后文本 LAAL 仍明显高于 B，再做 S2。S3 和 S4 会改变“与 B 同数据”的设定，需要你决定。

## 6. 结果：只改推理的两个版本（2026-11-28 16:16–16:23 CET，用户同意 BLEU 可略降）

**实验设置：**
- 两个版本并行解码：T 用 0–3 号卡，TC 用 4–7 号卡，各约 6.5 分钟。
- 解码用同一个 checkpoint、同样的 6 段音频、同样的窗口、TTS 种子和循环保护。
- 脚本：`e10_multispk/decode_e10v3_latency.sh`；统计：`e10_multispk/analysis/arms_latency.py`，结果在 `output/demo_game_v3tc/arms_latency.json`。

**两个版本：**
- **T**：p(写) ≥ 0.3 就写（`--write_threshold 0.3`）。
- **TC**：在 T 的基础上，连续等满 4 步（2.56 s）就强制写（`--max_wait_steps 4`），共强制了 151 次。

**结论：**
- **TC 基本消除了大段等待。** 文本 LAAL 降到与 B 持平，或比 B 更低（下降 0.3–1.8 s）。>3 s 静音从 7–65 s 降到 0–20 s。gz02 剩下的 20 s 静音主要来自一个报错窗口。
- **代价是 BLEU 下降。**
  - 英→中下降 2.3–2.7。
  - 中→英：gz01 持平，gz02 下降 1.4，gz03 上升 1.1。
  - BLEU 的参考译文是自动生成的，且只有单个 seed。
- **T 的改善只有一半左右**，大段静音仍然很多。
- **Talker 报错（序列超过 2048 上限）**：TC 1 个窗口，T 3 个窗口，原 v3 2 个窗口。这与延迟无关，可以通过放大 `TalkerStreamState` 的 `max_len` 修复，但尚未处理。
