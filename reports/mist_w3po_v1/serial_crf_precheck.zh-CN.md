## 2. 条目、顺序与 κ

### 2.1 条目与顺序
- **条目**是 `sched_v1` / `sched_dev_v1` 中的块。每个块本身就是一个闭合的 G-STAR 段 `<spk><t_a>文本<t_b>`。
- ρ(c) = 启发式（v8 标签）调度下块 c 的提交读。B_r = {c : ρ(c) = r}，按标签（S）顺序排列。
- Π(B_r) = 满足"同一单元的块保持原顺序"的全部排列，标签顺序排第一。"上一读未闭合段的续写块排第一"这条约束**从不生效**：211,127 个历史中，以未闭合段结尾的为 0。
- \|B_r\| > 4 时只打分标签顺序。

### 2.2 κ：§13.2 原文的键不精确，改用一个同样只依赖集合的键
- **§13.2 原文**：按 (ρ, 单元源起点 a_u, 块序号) 排序。它**不等于** S 前缀：dev 7.2%、train 6.3% 的读不一致。
  - 每处不一致，第一个不同的位置上两个块都属于同一提交读。
  - 原因是 S（以及 v8 的训练行）在同一提交读内按块的提交时间排序，提交时间 = 源终点 + 1 s，也就是按**终点**排，而原文的键按**起点**排。
  - 样本中第一次出现不一致的位置：dev 17 个窗口里，12 个是"原文的键排在前面的块起点更早、终点更晚"（另一单元），5 个是"原文的键排在前面的是更早开始的单元的续写块"；train 34 个窗口里分别是 25 个和 9 个。
  - 例子（dev `IB4004_zh_0110` 第 3 次读，位置 1）：S 先写 `<|spk2|><|t11|>Well,<|t13|>`（860–1041 ms），原文的键先写 `<|spk3|><|t4|>And to drink their coffee.<|t17|>`（300–1393 ms）。
  - 换句话说，标签里先结束的短插话排在前面，而原文的键会把它排到更早开始的长段后面。
  - 逐处列表见 `cpu/kappa_s13_mismatch_sample.jsonl`。
- **实际使用**：κ = 按 (ρ, 源终点, 源起点, 块序号) 排序。
  - 它仍然只依赖集合，对给定集合与之前各读的写出顺序无关（有测试）。
  - **在两个数据集的每一次读上都与 S 前缀逐 token 一致**，而且没有用到块序号来打破平局：(ρ, 终点, 起点) 的平局为 0。
  - 样本另做两项核对，全部一致：
    - κ 字符串联合分词后与 S 前缀相同：dev 1,853 次读、train 3,093 次读；
    - 与 v8 自己的训练行相同：dev 1,277 行、train 2,148 行的 prefix 和 target 字符串，以及 end。
  - 打分进程在加载模型前会对自己的窗口再跑一遍这项检验，不通过就退出。
- **对 §13 的含义**：
  - 预检里 h_r 对同一读的所有 π 相同，所以只要键是精确的，打分结果与键的选择无关。
  - 但推理时的"集合状态历史开关"需要能从生成的 token 算出这个键。时间 token 是 80 ms 量化的，(ρ, 量化终点, 量化起点, 槽位) 在 train 0.85%、dev 1.06% 的历史上会因量化平局而偏离 S。
  - 所以 §13.2 应改写为"按 (ρ, 源终点, 源起点) 排序"，并注明量化平局的处理办法。

## 6. P2：机制检验（预登记形式）

f = argmax_x log p(y_x \| x≤t_r, c, h_r)（在所有能排第一的条目里取）。P_complete(f) = Σ_{π: π₁ = f} e^{ψ(π)} / p(y_f \| ·)。

| dev | n | f ≠ 标签首项：中位数（四分位，最大） | n | f = 标签首项：中位数（四分位，最大） | 同一批读中，以标签首项起手的 P_complete 中位数 |
|---|---|---|---|---|---|
| 全部可换序读 | 39 | **1.3×10⁻¹⁰**（1.6×10⁻¹⁶–1.2×10⁻⁷，0.008） | 64 | 3.1×10⁻⁸（2.0×10⁻¹²–2.7×10⁻⁴，0.61） | 7.5×10⁻⁴ |
| 含 ≤1 s 重叠单元的读 | 21 | 3.1×10⁻¹⁰（…，0.0016） | 39 | 6.8×10⁻⁸（…，0.096） | 1.2×10⁻³ |
| 非最终读 | 17 | 3.1×10⁻¹⁰ | 33 | 1.5×10⁻⁹ | 1.6×10⁻⁴ |
| 最终读 | 22 | 5.3×10⁻¹⁴ | 31 | 1.4×10⁻⁶ | 1.4×10⁻³ |

train：全部 5.3×10⁻⁸（n = 62）对 1.2×10⁻⁵（n = 105）；含 ≤1 s 重叠单元的读 6.6×10⁻⁸ 对 3.2×10⁻⁶。f ≠ 标签首项的读占 dev 37.9%（含 ≤1 s 重叠单元的读中 35%）、train 37.1%。

**规则判定**：f ≠ 标签首项时的中位数远低于 0.8，**不停止**。

**但 P2 的这个形式没有判别力**：
- P_complete 是剩余条目**逐 token 精确参考译文**的概率（加上 e_r），剩余文本只要有十几个 token，概率就是 10⁻³ 到 10⁻¹⁰ 量级。f = 标签首项时它也接近 0，最大值只有 0.61。所以"H 不成立 → P_complete ≈ 1 → 停止"这条推理在数值上不可能出现，停止线 0.8 永远不会被触发。
- 两组的中位数虽然相差约 240 倍，但不能当作 H 的证据：
  - 两组剩下的条目不同（f ≠ 标签首项时剩下的是标签首项，反之亦然），内容概率不可比；
  - 而且 f 本身就是按"首项概率最大"选的。对 2 条目的读，P_c(f) / P_c(ℓ) = [q(fℓ) / q(ℓf)] × [p(y_ℓ) / p(y_f)]，在构造上就偏向小于 1。
- 这是预登记设计的缺陷，我在写脚本时没有发现，看到结果后才意识到。

## 7. 事后诊断（看到 P2 结果后才加的，不是停止规则）

为了去掉内容概率，用同一批已存的打分（没有新的前向），只看**写完首项 x 之后那一个位置**的结构决策：
- **p_open_rest(x)**：下一个 token 是某个剩余到期条目的说话人 token（不同的说话人 token 相加）；
- **p_end(x)**：下一个 token 是 e_r，即 `<wait>`；最终读上是 `<eos>`，`<wait>` 已被屏蔽；
- **p_other(x)** = 其余（别的说话人、时间或文本 token 等）。
- 2 条目读另外计算**结构完成概率** p(另一条目的说话人 token \| y_x) × p(e_r \| y_x, y_另一条目)，即把另一条目的文本和时间 token 去掉之后的 P_complete。

**dev（主要）**，中位数（四分位）：

| 组 | f ≠ 标签首项：p_open_rest(f) / p_end(f) | f = 标签首项：p_open_rest(f) / p_end(f) | 同一批 f ≠ 标签首项的读中，标签首项起手的 p_open_rest | 2 条目结构完成：f ≠ / f = / 同读标签首项 |
|---|---|---|---|---|
| 全部（39 / 64） | **0.83**（0.33–0.97）/ 0.001 | **0.82**（0.45–0.97）/ 0.011 | 0.78 | **0.70 / 0.73** / 0.37（n = 27 / 46） |
| 含 ≤1 s 重叠单元（21 / 39） | 0.71 / 0.001 | 0.81 / 0.017 | 0.67 | **0.29 / 0.57** / 0.37（n = 15 / 25） |
| 非最终读（17 / 33） | 0.57 / 0.23 | 0.60 / 0.06 | 0.58 | 0.34 / 0.37 / 0.26 |
| 最终读（22 / 31） | 0.97 / 0.000 | 0.94 / 0.001 | 0.82 | 0.94 / 0.92 / 0.38 |
| 含 ≤1 s 重叠单元，非最终读（7 / 23） | 0.21 / 0.39 | 0.66 / 0.05 | 0.65 | 0.09 / 0.36 / 0.51（n = 5 / 16） |

**train（参考）**：

| 组 | f ≠：p_open_rest / p_end | f =：p_open_rest / p_end | 2 条目结构完成 f ≠ / f = |
|---|---|---|---|
| 全部（62 / 105） | 0.75 / 0.039 | 0.65 / 0.016 | 0.45 / 0.43（n = 43 / 81） |

其他事实：
- f ≠ 标签首项的读里，"标签首项是 ≤1 s 重叠单元而模型偏好先写别人"的只有 dev 3 个、train 8 个。也就是说，在金标历史下，§13.1 假设的那种局面（先写对方、插话留在后面）在教师强制的多条目读里很少出现。
- 最终读上，写完首项后几乎从不直接 `<eos>`（中位数 ≤ 0.001），而以 ≥ 0.94 的概率打开下一个到期条目，不论首项是否是标签首项。

**解读**：
1. 整体看，在金标、集合状态历史下，v8 先写了它偏好的非标签首项之后，仍然**以与标签首项起手相同的概率**去写剩余到期条目（dev 0.83 对 0.82，2 条目结构完成 0.70 对 0.73；train 同样无差别）。这**不支持** H，即"一旦先写对方，就不知道还要补写插话，于是写 `<wait>`"。
2. 唯一指向 H 的是 dev 中"含 ≤1 s 重叠单元、非最终读"的小子组：p_open_rest 0.21 对 0.66，p_end 0.39 对 0.05。但 n 只有 7（2 条目结构完成只有 5 个），train 的同一子组（n = 24）没有差别（0.57 对 0.48）。不能下结论。
3. 所以在线解码里的"顺序→漏译"（检查 A 的 36–51%）多半不是这个教师强制下可见的机制。可能的原因（**都没有检验**）：
   - 在线时历史是模型自己的输出（措辞、切分、说话人都可能不同），不是 κ 规范化的金标历史；
   - 漏掉的插话可能落在 p_other 里，例如被并进对方的段，或写成了别的说话人；
   - 检查 A 的 (i) 类定义较宽（`sched_precheck_v8.zh-CN.md` §8.5）。
4. P1 显示顺序维度上没有不动点。这本来是 1′-b 相对 1′ 的优势；但如果 H 不成立，SerialCRF 的训练信号主要是在重新分配顺序的权重，不一定能减少漏译。

## 8. P3：标签路径一致性

ψ(标签顺序)（本预检：提示 + h_r + B_r^标签 + e_r）对比一′ 预检的 sum(tok_lp[r, β_{r−1}:β_r]) + end_lp[r, β_r]（提示 + 完整 S），同样的读，同样的引擎代码。

| | dev（167 次读，3,048 个 token） | train（276 次读，4,972 个 token） |
|---|---|---|
| \|Δψ\| 中位数 / p90 / 最大 | 0.263 / 0.818 / 2.97 | 0.257 / 0.817 / 2.08 |
| 逐 token 有符号差的均值 | −0.0005 | +0.0009 |
| 逐 token \|d\| 中位数 / p99 / 最大；\|d\| > 0.5 的占比 | 0.020 / 0.51 / 2.17；1.1% | 0.020 / 0.47 / 1.09；0.86% |
| e_r 的 \|Δ\| 最大 | 0.31 | 0.65 |

- 差异**没有偏差**：均值约为 0，读级有符号差的中位数是 0.000。差异与读长度只有弱相关（r = 0.13）。
- 这是 bf16 下批次组成和填充长度不同带来的噪声：两次运行一次批内是同一窗口的 4 次读、提示含完整 S，另一次是不同 π 混批。在 MoE 上，个别 token 可以变化 1–2 nats。
- 不存在位置错位：错位会差几十 nats。
- 冒烟时我自己设的门槛（读级中位数 < 0.2 nats）定得太严，冒烟因此被判为"未通过"。逐 token 检查（中位数 0.01–0.03，e_r 的差 ≤ 0.003）确认对齐无误后，才启动正式分片。这个门槛只是运行检查，不是预登记的内容。
- §13.6 里"开关打开或关闭时 ψ 逐位相同"在 bf16 批量计算下不可能逐位成立。可以逐位成立的是**输入 token 序列**：κ 历史 = S 前缀，已由精确性检验逐 token 证明。ψ 只在上述噪声范围内一致。

## 10. 结论与建议

1. **按预登记规则：GO。** 精确性检验通过（用的是修正后的键），P0 = 73.5% ≥ 30%，P2 没触发停止。
2. **实质上，本预检没有证实机制 H，建议暂缓实现 1′-b 的训练代码，由用户决定。**
   - P2 的预登记形式在数值上不可能触发停止，等于没有检验 H。
   - 事后的无内容诊断整体上与 H 相反：写完非标签首项后的完成率不低于写完标签首项后。
   - 只有一个 n = 5–7 的 dev 子组指向 H，train 不复现。
3. 如果用户仍想推进，可选做法：
   - (a) 重新预登记一个无内容的 P2：2 条目读的结构完成概率，以 f = 标签首项为对照，阈值事先写定。在**全部** dev 参考窗口上重测：3,366 个窗口，2,117 个多条目读，其中 1,484 个可换序，共 5,250 次前向。这样可以加大"含 ≤1 s 重叠单元、非最终读"子组的样本量。CPU 部分已就绪，4 卡约 10 分钟。
   - (b) 先在在线解码里定位漏译到底落在哪里：p_other 一类，或历史不是规范顺序。
4. 不论是否推进，§13.2 里 κ 的定义都要改成 (ρ, 源终点, 源起点)。

### 12.6 合起来看

- **H_final 不支持**：顺序→漏译只有 1/4 在最终读到期，而且最终读上 v8 几乎不会提前 `<eos>`。
- **H_rec 按规则不确定**，但没有任何证据表明缺失历史会降低下一读开头的补写概率。
- 证据指向一条**链**：
  1. 非最终读上，写完偏好首项后经常 `<wait>`（D2：62%，只用说话人 token 时 46%）；
  2. 到下一读，如果先写新到期的条目，回头补写被推迟的插话的概率就和 `<wait>` 相当或更低（D3 的 R_end）。
- 这是推断，没有直接检验。直接检验需要在线解码中的逐读轨迹。
- 对 1′-b 的含义：
  - 只在同一读内对顺序求和的 v1 覆盖不到这条链；
  - 它更接近 §13.2 的 v2（跨读补写）。
  - 是否继续由用户决定。
