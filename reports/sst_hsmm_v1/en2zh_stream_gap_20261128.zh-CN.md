# en2zh 流式损失从哪来，Thinker 还能怎么提升 BLEU（2026-11-28，只做分析）

- 数据：测试集已有输出，未跑模型，只用 CPU。判断"能不能做"只用开发集；测试集只出上限，只报告。
- 脚本在 `experiments/sst_hsmm_v1/en2zh_analysis/`：
  - a18：差距分解；
  - a18b：例子；
  - a19：oracle 等待；
  - a19b：句末感知等待；
  - a20：句末可预测性，开发集 pfb0。
- 口径：
  - 官方归一化，5 个测试格平均的文本 BLEU；
  - 离线上限 = wave17 读入完整音频的贪心解码；
  - 时延代理 = 输出单位的平均写出时间。用 p3hk2 标定：代理 −0.183 s 对应 D2 −0.242 s。

## 1. 先回答：Thinker 该提 BLEU 还是 COMET

在我们 15 个系统上，相对 p3hk：

| 相关系数 | en2zh | zh2en |
|---|---|---|
| ΔASR-BLEU 与 Δ文本 BLEU | 0.94（斜率 0.49） | 0.97（斜率 0.90） |
| ΔASR-BLEU 与 Δ文本 COMET | 0.54 | 0.39 |

最终的 ASR-BLEU 跟着 Thinker 的文本 BLEU 走，Thinker 的 COMET 提升基本传不过去。所以要让 ASR-BLEU 涨，Thinker 必须提文本 BLEU，也就是保持和参考一致的用词与语序。

## 2. p3hk 与离线上限之间的 1.81 分差距

把一类句子的输出换成离线上限，看能找回多少分：

| 类别 | en2zh 句数 | en2zh 找回 | zh2en 句数 | zh2en 找回 |
|---|---|---|---|---|
| 与离线完全相同 | 1329（54%） | – | 1813（63%） | – |
| 提前提交与离线一致，只在最后一读分歧 | 127 | +0.21 | 82 | −0.04 |
| **提前提交的文本已与离线不同** | 986（40%） | **+1.60** | 998（35%） | +1.44 |

提前提交分歧的细分如下：

| | en2zh | zh2en |
|---|---|---|
| 第一个分歧在块的最后一个单位 | 18% | **41%** |
| 第一个分歧在离块尾 ≥ 3 个单位处 | **41%** | 21% |
| 同长换词（近义词）：找回 | −0.01 | +0.21 |
| 增删 / 结构不同：找回 | +0.72 / +0.90 | +0.87 / +0.36 |

- zh2en 的分歧多是块尾提交过早，属于局部问题。
- en2zh 的分歧在块内部，是**语序**问题。近义词替换不扣分。
- 例子：
  - 原文 "Osan Station is a large subway station located in the heart of Osan."
    - 离线和参考："Osan站是位于Osan市中心的一个大型地铁站"
    - 流式先提交："Osan站是一个大型地铁站"
  - "However" 放在句尾的原文，离线和参考把"然而"提到句首。
  - "Limited reliable information is available about …"，离线把"关于…"提到句首。
- 中文参考（RealSI 是人工逐句翻译，带术语表）把后听到的修饰语、状语和话题提前。按原文顺序提交的同传式输出因此被扣分。

## 3. 只调提交时机（保持 base 用词）有没有空间

| | en2zh | zh2en |
|---|---|---|
| 降 θ 曲线：每秒时延换多少文本 BLEU | **3.4** | 1.7 |
| oracle 等待（已知会分歧，等到草稿出现离线语序再提交） | +1.60 / +0.377 s = 4.2 BLEU/s | +1.44 / +0.302 s = 4.8 BLEU/s |
| 分歧句中，非最后读的草稿从未出现离线语序 | **87%**（859/986） | 89% |

- en2zh 的 BLEU 对时延的敏感度是 zh2en 的两倍。
- 即使知道哪些句子会分歧，也只比降 θ 好一点：87% 的重排要到整句听完、最后一读才出现在草稿里，所以等待就等于等到句末。

句末感知等待（假设准确知道"源语音还剩不到 W ms"，这段时间内不做中间提交）：

| W | en2zh 文本 BLEU 上限 / 时延 | 每秒 | zh2en |
|---|---|---|---|
| 500 ms | +0.37 / +0.016 s | 23.6 | +0.20 / +0.014 s |
| 800 ms | +0.50 / +0.038 s | 13.1 | +0.59 / +0.037 s |
| 1200 ms | +1.12 / +0.113 s | 9.9 | +0.94 / +0.089 s |

- 这是唯一明显优于曲线的方向：按 W=1200 估算，用降 θ 补回时延后，同等时延下 ASR-BLEU 约 +0.36。
- 但它依赖提前预测句末。开发集 pfb0（en2zh，heal@0.75）上，用模型自己的信号（草稿句末标点的对数概率）预测"这是最后一次中间读取"：
  - AUC：edev 0.69、cvdev 0.72；
  - 精度 0.28 / 0.35，召回 0.63 / 0.68；基础比例 0.18 / 0.21。
  - "草稿内容不变"几乎没有信号（AUC 0.50 / 0.59）。
- 按这个误判率粗算，每个真正的末读要伴随约 2.3 个误判；误判也要多等一个读取间隔，合计约 3 BLEU/s，与降 θ 持平。

## 4. 结论

- en2zh 在 BLEU 上的天花板来自语序。中文参考是离线翻译，把后听到的信息前置；同传系统在相同时延下只能按原文顺序先说。
- 不改用词的提交策略赢不了：oracle 只到 4.2 BLEU/s；句末感知方向理论上可以，但模型自身对句末的预测太弱。
- 改用词的 adapter 方法能降时延，但译文更"顺序化"，用词也不同：BLEU 掉，COMET 显著涨（`en2zh_cause_bleu_vs_comet_20261128.zh-CN.md`）。
- zh2en 不同：分歧集中在块尾（局部），英文按词计分，降 θ 的代价只有一半，所以同类方法在 zh2en 上两个指标都有效。
- 论文写法建议：
  - en2zh 报 ASR-BLEU + ASR-COMET + 本分析（语序分解、oracle 上限、两个方向 BLEU-时延斜率的差异）；
  - 主方法 p3hk 相对 B_b 两个方向都有效；预判扩展在 zh2en 上 BLEU、COMET 都有效，在 en2zh 上是"语义和时延更好，离线参考 BLEU 受语序惩罚"。
- 如果还要在 BLEU 上试一次，唯一有上限支撑的方向是**更准的句末预测**，比如基于音频韵律的预测器。这要新增一个预测部件，风险高，需要你决定。
