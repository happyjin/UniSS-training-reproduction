# en2zh 为什么一直无效 — 根因分析（2026-11-27 晚）

数据来源：
- change 56 测试输出（`pv3/comet/dump.jsonl`，5 个 cell，2442 句）；
- 各系统的 thinker blocks；
- dev 运行结果（`pf*/dev`）；
- 新跑的整句离线解码 `pv3/offtag`（脚本 `experiments/sst_hsmm_v1/pv3_offtag.sh`，只做报告，不用于选择）。

所有 BLEU 都用官方算法（`wave2_s1_score.Bleu`，即 `normalize_for_bleu`：去标点、繁转简、逐字切分，拉丁字母也逐个算一个 token），并按 5 个 cell 取平均。分析脚本在 `experiments/sst_hsmm_v1/en2zh_analysis/`（a3 提交拆分，a4 前段与尾部精度，a5 英文术语，a8 反事实替换与用词漂移，a9 dev 两种 BLEU 对比，a10 整句离线）。

## 结论（一句话）

en2zh 的损失和流式、预判、提交策略都无关。原因是所有预判 LoRA 都在 UniST 的参考译文上训练，而 UniST 的 en2zh 译文风格和测试参考不一致：
1. 英文人名、术语几乎全部被音译或意译成中文；
2. 语体偏书面。

LoRA 把这种风格带进了每一句输出。与此同时，dev 筛选的 BLEU 算法和官方不一致，edev 又和训练数据同风格，所以 dev 一直看不到这个问题。

## 1. 损失和流式无关：整句离线也一样掉

在 dev（wave2_S1）上做整句音频的贪心解码，不流式、不提交、不预判，用官方 BLEU：

| en2zh 整句离线 | 全部（n=1274） | 参考含英文（n=374） | 参考不含英文（n=900） | 输出拉丁字母/100 字 |
|---|---|---|---|---|
| wave17（p3hk 的起草器） | 41.31 | 32.65 | 47.27 | 6.5 |
| p2ft（E1/H3/E1+D1 的起草器） | 36.86（**−4.45**） | 23.63（**−9.02**） | 45.58（−1.69） | 1.4 |
| h4m（H4，只用整句数据训练） | 36.74（−4.57） | 23.88（−8.77） | 45.22（−2.05） | 1.5 |
| h1tr（H1 的起草器） | 37.32（−3.99） | 25.02（−7.63） | 45.30（−1.97） | 1.7 |

- H4 的 LoRA 只用整句数据训练，完全没有前缀和预判，损失却几乎一样。所以损失来自**在 UniST 译文上做微调**本身，和"预判"无关。
- 在测试的流式输出里还有一个旁证：E1/H3 提前提交的部分和最后整句读出时写的尾部，字级精度都下降约 3 个点（提前部分 68.4→65.4，尾部 63.4→60.5）。损失均匀分布在整句里，不是集中在预判出来、提前提交的内容上。

## 2. 损失由什么构成（测试集，H3 对 p3hk）

| | ASR-BLEU 差 | 文本 BLEU 差 |
|---|---|---|
| 总差距 | −1.70 | −3.33 |
| 只把"参考含英文"的 578 句换回 p3hk 的输出后 | −1.01 | −1.09 |
| 英文术语这一项能解释的比例 | **41%** | **67%** |

**(a) 英文人名和术语（主要影响 OBSI 的 3 个 cell）**
- 测试参考保留英文的程度：OBSI 每 100 字约 21 个拉丁字母，RealSI 只有 0.8。
- UniST 训练参考只有 0.30，含英文词的行只占 1.4%。例子："Talyllyn's" 被译成"塔利林"。
- 结果是参考里的英文词能在输出里原样找到的比例下降：p3hk 18.9%，S3 11.4%，E1/H3 只有 7.2%。例子：
  - "Letterman" 被译成"莱特曼"；
  - "Valete and Sam the Kid" 被译成"瓦莱特和山姆"。
- 官方 BLEU 把英文拆成单个字母，"Letterman" 一个词就算 9 个 token，所以这一项被放大。如果把英文词当作一个 token，文本差距会从 −3.33 缩小到 −2.84，但仍然很大。
- 分 cell 的文本 BLEU 差（H3 对 p3hk）：OBSI 是 −6.2、−4.2、−3.3，RealSI 是 −1.0、−1.9。

**(b) 语体漂移（影响所有 cell，占 ASR-BLEU 损失的约 59%）**
- 在参考不含英文的句子上，H3 新增而参考里没有的字对，最多的是"认为、一位/一名、女性、进行、实际上、正在、事情、非常"。
- 被它替换掉、而参考里有的字对，最多的是"觉得、一个、女人、东西、但是、很多"。
- 也就是说，测试参考是口语化的口译风格，而 LoRA 学到的是 UniST 的书面风格。例子："teachers" 被译成"教师"，参考是"老师"。
- 输出也略长一些：RealSI 上长度比 1.058，p3hk 是 1.037。
- 语义没有变差：这些句子的 COMET 平均 +0.0035。

**(c) 只占很小一部分的是真正的预判错误**，例如在句首提前提交了幻觉内容"停机时间。"。

## 3. dev 为什么没发现：两处盲区

1. **BLEU 算法不一致。** 所有 dev 和选择脚本都用原始 sacrebleu，包括 `pf_analyze`、`pick_theta*`、`pick_h*`、`d3_analyze`、`offdev_score` 等。原始 sacrebleu 保留标点，英文词整体算一个 token，和官方测试 BLEU 不同。下表是 cvdev en2zh 相对 B0 的差值，同一批输出：

   | | E1 | H3 | H1 | E1+D1 | H4 | D1 |
   |---|---|---|---|---|---|---|
   | 原始 sacrebleu（dev 用的） | +0.50 | +0.77 | +0.77 | +1.00 | −0.50 | +0.24 |
   | 官方 BLEU（测试用的） | **−4.92** | **−4.71** | **−4.42** | **−4.58** | **−5.58** | −0.73 |

   zh2en 两种算法基本一致（例如 E1 −2.14 对 −2.64），所以这个盲区只影响 en2zh。

2. **edev 和训练数据同风格。** edev 来自 UniST-Emilia，参考里几乎没有英文（0.48/100 字），语体也是 UniST 风格。所以 LoRA 在 edev 上反而大幅加分：en2zh 官方 BLEU +1.9～+2.5，zh2en +4.7～+5.2。

结果是 dev 筛选一直在"批准" en2zh 的 LoRA 方法。从 D3/S1、P2F/S3 到 E1/H1/H3，每一轮都踩了同一个坑。

## 4. 为什么 zh2en 有效、en2zh 无效

- **只有预判能缩短占主导的"内容稳定滞后"**，而预判只能通过 LoRA 起草器实现。不做预判的方法（θ、D1、SAP、校准、H3 门控）只是沿原来的时延-质量曲线移动，曲线不外移。
- **zh2en**：目标语是英文，不存在保留英文的问题。整句离线时 LoRA 在 wave2_S1 dev 上也掉 2.5～2.6（w17 30.64，p2ft 28.01，h1tr 28.11），但测试集上的语体损失小（ASR −0.35～−0.66），时延收益（−0.2～−0.32 s）足以抵消，所以有效。
- **en2zh**：LoRA 带来的风格损失约 −1.7 ASR-BLEU（文本约 −3.3），远大于 0.2～0.4 s 时延收益在连线上能换回的分数。所以每个预判方法在 en2zh 上都无效，和用哪种预判机制无关。
- COMET 不惩罚"莱特曼"和"Letterman"的差别，也不惩罚"认为"和"觉得"的差别，所以 COMET 判这些方法更好。

## 5. 建议（按优先级；都需要你同意后才跑）

**A. 先修测量（必须做，只用 CPU，约 30 分钟）**
- 把 dev 和选择脚本的 BLEU 统一成官方 `Bleu`。
- en2zh 的 dev 筛选以 cvdev 为主，edev 只作参考。
- 新增一道便宜的前置门槛：任何 LoRA 起草器在跑流式之前，先做整句离线官方 BLEU（wave2_S1 dev，约 15 分钟），要求不低于 wave17 − 0.5。
- 用新的 BLEU 重算已有的 dev 结果，看之前哪些 θ 或方法选择会翻转。
- 这一步在 prereg 里记为修订。如果这道门槛早就存在，这几轮的 LoRA 方法在训练后 15 分钟就会被拦下。

**B. 去掉预判 LoRA 的风格副作用，同时保留预判带来的时延收益**

两个方案可以并行跑，每个是 1 次训练加离线前置检查，通过后再跑测试：
- **B1 保留英文术语的训练目标（数据修正，仍用同一份 UniST 数据）。** 用 UniST 已有的 OmniAlign 词对齐，把源句里的人名、缩写、专有名词对应的音译片段替换回英文原词，再按 E1 的配方重新训练。
  - 依据来自开放数据：cvdev（CoVoST）的参考同样保留英文，每 100 字 20 个拉丁字母，不是从测试集学来的。
  - 局限：只能解决 41% 的 ASR 损失，语体问题还在，单独用大概率仍过不了判定。
- **B2 只学预判的 LoRA。**
  - 训练：去掉整句样本，前缀样本只在"未听到部分"的 token 上计算损失，已听到部分的 token 不算损失。
  - 推理：最后整句读出时用 base 模型（S3 的忠实收尾）。
  - 目的：让 LoRA 只学"往后猜"，不学"改写已听到的内容"。英文术语和语体都应保持 base 的风格。
  - 这比 B1 更接近根本问题，也有方法上的新意（解耦"说什么"和"何时说"）。

**C. 推理期方案（不训练，可选）**：在起草时把 Thinker 转写里出现的英文专有名词作为词汇约束，即受约束解码（Hokamp & Liu 2017；Post & Vilar 2018）。风险是 RealSI 的参考把人名译成中文，两个测试集的约定相反，收益不确定。

**需要你决定**：
1. A 是否立即执行（建议执行）；
2. B1 和 B2 是否并行跑（建议两个都跑）；
3. B1 会改写 UniST 的参考译文（只换英文术语），这算不算"换数据"，需要你确认。
