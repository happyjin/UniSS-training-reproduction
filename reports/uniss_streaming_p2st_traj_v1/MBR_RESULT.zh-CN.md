# MBR 选择:训练无关的贝叶斯决策,在两个轴上同时胜过 DPO

2026-09-15。RealSI 777 条全集,文本 BLEU 与静音均在同一批候选上测量。
BLEU 用项目口径(`evaluation.text_metrics`:去标点 + 简体化后 sacrebleu)。

## 〇、适用范围(先读这一节)

**这里测的 MBR 是"整句选择",在真正的流式部署里不可用。**

每个候选本身是严格流式的(固定 640 ms 读网格),但**选择发生在 8 条全部跑完之后**。
live 系统必须边生成边发声、发出的音频无法撤回;要等 8 条都结束才能选,
等于把延迟推到整句末尾,流式契约就破了。

算力上也有一笔账:单遍 RTF 已是 1.41,8 遍串行约 RTF 11;
要维持 RTF 1.41 需要 **8 倍硬件**同时跑 8 条流。

所以本文数字的准确定位:

* **离线 / 可重录场景**:直接可用;
* **流式场景**:这是**选择规则的上界**,不是可部署配置。

流式可行的版本是**逐片段增量 MBR** —— 每个读步采 K 条续写,
只对"这一片段发什么"做贝叶斯选择。它保住流式契约,但 utility 必须定义在
**部分假设**上,是一项新工作。

(同一限制也适用于本项目更早那次重排序实验的 0.198 → 0.095,当时没有标注,这里补上。)

## 一、结论

**在同一个候选池上,MBR 比我们手搭的分层奖励更好,而且比 DPO 后的模型
在静音和质量两个轴上都更好 —— 代价是 8 倍推理成本。**

| 系统 | 推理 | en→zh | zh→en | 合计 | 静音 |
|---|---|---:|---:|---:|---:|
| 单条采样候选 | 1× | 19.50 | 13.98 | 33.48 | 0.2076 |
| **dpo_base 贪心(当前部署)** | **1×** | 21.69 | 16.26 | **37.95** | 0.1981 |
| pf_guard 贪心(DPO 后) | 1× | 22.32 | 16.43 | 38.74 | 0.1744 |
| pf_paper 贪心 | 1× | 21.15 | 13.88 | 35.03 | 0.1579 |
| **MBR-chrF** | 8× | 22.25 | **17.14** | **39.39** | 0.2053 |
| **MBR-chrF + flow 0.25** | 8× | **22.35** | 17.05 | **39.40** | **0.1462** |
| **MBR-chrF + flow 0.5** | 8× | 21.94 | 17.10 | 39.04 | 0.1251 |
| **MBR-chrF + flow 1.0** | 8× | 21.82 | 16.83 | 38.65 | **0.1019** |
| MBR-chrF + flow 2.0 | 8× | 21.25 | 16.13 | 37.38 | 0.0843 |
| MBR-BLEU | 8× | 21.36 | 16.11 | 37.47 | 0.2133 |
| *oracle(选到最好的那条)* | — | 27.96 | 24.09 | *52.05* | 0.2046 |
| *最安静(纯压静音)* | — | 19.12 | 13.27 | *32.39* | *0.0742* |

相对**贪心部署基线** 37.95 / 0.1981:

* **MBR-chrF:+1.44 BLEU**,静音基本不变;
* **MBR + flow 0.25:+1.45 BLEU 且静音 −5.2pp** —— **静音项在这一档不花任何 BLEU**
  (39.40 对纯 MBR 的 39.39),是当前最好的工作点;
* MBR + flow 0.5:+1.09 BLEU,静音 −7.3pp;
* MBR + flow 1.0:+0.70 BLEU,静音 −9.6pp。

候选池的内部一致度(平均两两 chrF)为 **48.34** —— 这个数越低,
说明候选彼此越不同、MBR 可利用的分歧越多。

**它同时压过两个 DPO 检查点**:pf_guard 是 38.74 / 0.1744,pf_paper 是 35.03 / 0.1579,
而 MBR + flow 0.5 是 **39.04 / 0.1251** —— 更高的 BLEU 和更低的静音。
而且这批候选出自 **DPO 之前**的 `dpo_base`,所以这是"旧模型 + 更好的选择规则"
胜过"新模型 + 贪心"。

## 二、两个防止高估的对照

这两条都写在这里,因为少了任何一条都会把结论说大。

1. **不能拿单条采样候选当基线。** 它只有 33.48,用它作比会把 MBR 的收益
   从 **+1.44 说成 +5.91**。实际部署是贪心解码,基线必须是 37.95。
2. **纯压静音会伤质量。** "最安静"策略拿到 0.0742 的静音,但 BLEU 掉到 32.39,
   **低于贪心基线**。这正是 NaturalFlow 论文警告的"激进压静音导致语义退化",
   在我们的数据上复现了一次。flow 权重从 0.5 提到 2.0 也呈现同一趋势
   (39.04 → 38.65 → 37.38)。

## 三、为什么 chrF 比 BLEU 好用

utility 用 chrF(39.39)明显优于用 sentence-BLEU(37.47)。
原因是 sentence-BLEU 在短句上有大量零 n-gram 匹配,对 8 条互为伪参考的短候选
几乎不可分;chrF 是字符级的,在同样的候选上仍能给出连续的相似度。
这与 MBR 文献里 chrF/COMET 优于 BLEU 作为 utility 的结论一致。

## 四、离上界还有多远

oracle 是 52.05,即池子里"如果每次都选中最好的那条"能到的水平。
MBR 把贪心到 oracle 的差距填掉 **(39.39 − 37.95) / (52.05 − 37.95) = 10.2%**。

也就是说:**候选池里有远超当前选择规则能提取的质量**。
这指向两个方向 —— 更好的 utility(COMET 类的神经度量,但要 GPU),
或更大的候选池(论文用 32 个,我们用 8 个)。

## 五、复现

```
PYTHONPATH=. $PY -m experiments.uniss_streaming_p2st_traj_v1.evaluation.mbr_select \
  --rollout-root reports/uniss_streaming_p2st_realsi_v1/rollout \
  --arm r7_01 ... --arm r7_08 \
  --utility chrf --utility bleu --flow-weight 0.5 --flow-weight 1.0 --flow-weight 2.0 \
  --workers 96
```

纯 CPU,96 进程,777 × 8 候选约 40 秒。


## 六、在 DPO 之后再做 MBR:不叠加

用 pf_guard 自己的权重重采 8 个候选(除检查点与种子外与基线池逐项一致):

| | 基线池(dpo_base) | pf_guard 池 |
|---|---:|---:|
| **池内一致度**(平均两两 chrF) | 48.34 | **54.58** |
| 贪心(1×) | 37.95 / 0.1981 | 38.74 / 0.1744 |
| MBR | 39.40 / 0.1462 | **39.44** / 0.1851 |
| MBR + flow 0.25 | 39.40 / 0.1462 | 39.29 / 0.1401 |
| MBR + flow 0.5 | 39.04 / 0.1251 | **39.18 / 0.1153** |
| MBR + flow 1.0 | 38.65 / 0.1019 | 38.55 / **0.0925** |
| *oracle* | *52.05* | *53.50* |

**质量天花板几乎相同:39.40 与 39.44,差 0.04。** 两条路各自把文本 BLEU
推到约 39.4 就停住,叠加没有额外质量收益。

诊断给出的原因有两条,而且互相印证:

1. **池子变窄**:一致度 48.34 → **54.58**。DPO 锐化了分布,候选彼此更像,
   MBR 可利用的分歧变少 —— 相应地 MBR 相对贪心的增益从 **+1.45 缩到 +0.70**。
2. **修的是同一批毛病**:两个天花板撞在一起。

**静音轴上两者确实叠加**:同等 BLEU 下 pf_guard 池的静音更低
(flow 0.5:39.18/0.1153 对 39.04/0.1251)。

### 对部署的判断

**pf_guard 贪心(1×)仍是该上线的配置。** MBR 在它之上只加 +0.70 BLEU,
却要 8 倍算力,且整句选择在流式下不可部署。DPO 的收益是推理免费的。

### 瓶颈在哪:不是模型,是选择信号

oracle 53.50 而 MBR 只到 39.44 —— 池子里**有 14 BLEU 是任何现有选择规则都没提取到的**,
提取率从基线池的 10.3% 降到 **4.7%**。
这说明"共识"(MBR 的 utility)是质量的**弱代理**,而不是池子没有好候选。
