# 把 SimulS2ST-Omni 的做法移植过来:详细计划

基于已 clone 的仓库全文、已下载的 10 个 demo 音频,以及本项目这几轮的全部实测。
**先说哪些能搬、哪些搬不了,再给分层计划。**

## 一、他们做对了什么 —— 逐条判定可移植性

| # | 他们的做法 | 证据 | 能否移植 |
|---|---|---|---|
| 1 | **显式 IDLE token**:每个 chunk 要么产出文本,要么产出 `DEFAULT_IDLE_TOKEN` | `_is_wait()`、`assistant_text = text if text else DEFAULT_IDLE_TOKEN` | **能,而且是核心** |
| 2 | **latency 作为条件输入**:system prompt 里写 `With Latency: {m}` | `prompt_formats.build_system_prompt` 的 `latency_suffix` | **能,很便宜** |
| 3 | **等时输出**:每消费 m 秒源音频必产生一次 WriteAction,不足用同分布静音码补齐 | `policy()`;`Pad generated_codes with silence codes` | **能(结构),但见 §二** |
| 4 | **粗读步**:chunk = m 秒(1000–5000 ms),`--min-start-sec` 默认 1.0 s | `chunk_duration = float(latency_multiplier)` | **能,今天就能做** |
| 5 | **有界历史窗**:`history_window_turns=30`、`overlap=8`,且都除以 m | agent 第 175–176 行 | 能,长篇时需要 |
| 6 | **wait 时合成静音走声码器** | `--enable-wait-silence-decode` | **搬了,无效,见 §二** |
| 7 | Thinker–Talker + VoiceBox/Vocos 架构 | README | **不能**,我们是单 Qwen0.5B + 级联 |
| 8 | 2000 小时配对 S2ST 数据 | README | 不适用,我们有自己的池 |

## 二、已经试过且失败的一条,必须先说清楚

**第 6 条我已经实现并实测,它不解决问题。** 给 `realsi_rollout.py` 加了
`--silence-fill`(用同一个 BiCodec 对 1 秒静音取码,按时间线插进码序列,整条一次性
解码):

| | 静音帧 RMS 中位 | 精确为 0 占比 |
|---|---:|---:|
| 我的 placed(数字零) | 0.000000 | 28.2% |
| **我的 isochronous(合成静音)** | **0.000009** | 27.5% |
| 他们的 VoiceBox | **0.000518–0.000698** | 1.0–11.4% |

**BiCodec 把静音码解成近乎真静音,比他们的声码器安静 60 倍。**
所以"填静音"这条路在我们的声码器上无效 —— **这是声码器差异,不是策略差异,
换个填充方式也救不回来。** 计划里不再包含它。

## 三、分层计划

### T1:今天就能做,零训练(已全部实测)

**T1.1 —— 把读步当作对外暴露的旋钮,而不是固定 160 ms。**

我的读步扫描(8 条长音频,域内 validation,C 已开 s1t0):

| 读步 | 首次发音 | 空档/条 | 内部静音 | 源ASR错 | **MT BLEU** | **ASR-BLEU** |
|---:|---:|---:|---:|---|---|---|
| **160 ms** | **1120** | 5.2 | 0.24 | 0.08/0.08 | 32.5/28.8 | 27.6/**16.9** |
| 320 ms | 1440 | 5.6 | 0.35 | 0.08/0.09 | 36.6/32.3 | 26.1/18.3 |
| 480 ms | 1920 | 4.0 | 0.31 | 0.10/0.09 | 36.4/32.2 | **28.5**/19.8 |
| **960 ms** | 2880 | 5.0 | 0.37 | 0.09/0.10 | **37.9/33.2** | 27.2/**26.7** |
| 1920 ms | 5760 | 2.4 | 0.53 | 0.09/0.09 | 37.4/31.5 | 25.5/20.6 |

**Zh→En 的 ASR-BLEU 从 160 ms 的 16.9 涨到 960 ms 的 26.7(+58%)**,
代价是首次发音 1120 → 2880 ms。**这正是他们 m 参数表达的取舍,而我们一直只跑了
一个点。** 动作:把 `--read-stride` 写进对外文档和默认配置表,按场景选:

* **低延迟场景**:160 ms(开口 1.12 s)
* **质量优先场景**:960 ms(BLEU 最高,开口 2.88 s)≈ 他们的 m=1

**成本:0(旋钮已存在)。收益:Zh→En ASR-BLEU +9.8。**

**T1.2 —— s1t0 设为默认。** 已完成并验证:RealSI 777 条上开口 −971/−830 ms,
ASR-BLEU 只花 −0.65/−0.32。

**T1.3(未做,建议补)—— 在 RealSI 777 条上跑 640 / 960 ms 两个读步。**
现在的读步扫描只在 8 条域内长音频上做过,公开基准上只有 160 / 4000 ms 两点。
补这两点才能画出和论文可比的完整曲线。**成本:2 × 约 15 分钟。**

### T2:核心移植 —— 固定 chunk 网格 + 显式 IDLE 监督(需要训练)

**这是唯一能同时解决"卡顿"和"真实口语上 ASR 崩塌"的一条,
而且它正是论文标题里的 "Explicit Trajectory Supervision"。**

**为什么必须做:** 已经五条独立证据指向同一处 —— 我们的训练从没见过固定读网格
(`task_samples_p2st.py:410` 是 `for event in trajectory.events`,切在 gold 词边界)。

**数据侧已验证可行。** 把 gold 事件重新分箱到固定 chunk,IDLE 比例:

| chunk | chunk 数中位 | **IDLE 占比** | 有内容 chunk | 文本字/chunk |
|---:|---:|---:|---:|---:|
| 160 ms | 31 | **84.1%** | 15.9% | 3.2 |
| 320 ms | 16 | 70.2% | 29.8% | 3.4 |
| **640 ms** | 8 | **50.7%** | 49.3% | 4.0 |
| 960 ms | 6 | 40.4% | 59.6% | 4.8 |
| 1920 ms | 3 | 21.2% | 78.8% | 6.7 |

**这张表本身就解释了 160 ms 为什么难:六步里五步该闭嘴。**
构造所需字段(`source_end_ms` / `target_text_delta` / `target_semantic_delta`)
数据里全都有。

**具体步骤:**

1. **新建实验目录** `experiments/uniss_streaming_p2st_isochronous_v1/`
   (不动 C 的任何文件,遵守"新建而非修改"的约定)。

2. **数据构造** `data/uniform_chunk_tasks.py`:
   * 对每条 gold 轨迹,按 chunk 大小 C 重新分箱;
   * 每个 chunk 一个训练样本,监督目标是该窗口内 gold delta 的合并,
     **没有则监督一个新的 IDLE token**;
   * **latency 条件化**:每条样本随机采 C ∈ {320, 640, 960, 1920},
     并在前缀里放一个 latency 条件 token(对应他们的 `With Latency: m`),
     这样**一个 checkpoint 服务所有读步**;
   * 保留 C 现有的三个 family(streaming ASR / MT / TTS)和 phase3 replay。

3. **IDLE token 的落地方式**:C 的词表里没有空闲 token。两个选项,建议第二个:
   * (a) 新增一个专用 token —— 要动词表,风险高;
   * (b) **复用现有的 `TOKEN_END_CONTENT` / 空 delta 语义**,即把
     "本 chunk 无新内容"训练成"立刻输出终止符"。**不动词表,零结构风险。**
     判据是终止符在 IDLE chunk 上的准确率。

4. **训练**:从 C 的 `iter_0004236` 继续,纯 CE(C 的胜因),
   按记忆里的规矩在第 100 / 200 步各评一次暴露早期缺陷,之后回到 400 步节奏。

5. **验收判据**(全部有现成基线):
   | 指标 | 现在 | 目标 |
   |---|---|---|
   | IDLE chunk 上正确闭嘴的比例 | 无(结构不存在) | ≥ 0.90 |
   | RealSI k1 中文源 CER | **0.804** | ≤ 0.40 |
   | RealSI k1 英文源 WER | 0.421 | ≤ 0.40 |
   | RealSI ASR-BLEU(placed) | 14.66 / 10.37 | ≥ 18 / 14 |
   | 长音频空档/条 | 5.2 | ≤ 2.5 |
   | 首次发音(RealSI, k1) | 1573 ms | ≤ 1600 ms(不退化) |

### T3:长篇才需要的(暂缓)

**有界历史窗 + 重叠**(他们是 30 turn 窗、8 turn 重叠,且都除以 m)。
我们目前只做句级,篇章级还卡在 KV cache 复用上。**等 T2 做完再说。**

## 四、明确不做的

1. **填静音** —— §二已实测无效(BiCodec 静音比他们安静 60 倍)。
2. **换 Thinker–Talker 架构** —— 那是重写整个系统,不是移植。
3. **淡入淡出 / 调语速** —— 之前两轮都已实测无效
   (切口阶跃只有 p99 的 0.23–0.44,没有咔哒可消;speed 0.7–0.9 上最长空档纹丝不动)。
4. **δ 式无条件写** —— m3 已把这条路走到头(开口 320 ms,ASR-BLEU 1.36)。

## 五、执行顺序与预期

| 步 | 内容 | 成本 | 预期收益 |
|---|---|---|---|
| 1 | T1.1 把读步写进配置表,按场景选 | 0 | **Zh→En ASR-BLEU +9.8**(160→960 ms) |
| 2 | T1.3 在 RealSI 上补 640 / 960 ms 两点 | 约 30 分钟 | 得到与论文可比的完整 (延迟, BLEU) 曲线 |
| 3 | **T2 固定 chunk + IDLE 监督训练** | 一次训练 | 目标见验收表;这是唯一能同时修卡顿和真实口语 ASR 的一条 |
| 4 | T3 长篇历史窗 | 待 KV cache | 篇章级才需要 |

**一句话:能搬的是「训练时就按固定 chunk 走,并且显式监督什么时候闭嘴」和
「把 latency 当条件输入」;搬不了的是他们的声码器和架构;
而"填静音"这条看起来最像的,我试过了,在我们的声码器上无效。**

## 好消息:第 1 条的成本比我原先估的低得多

我原以为算 NIR 需要重跑 SimAlign。**实测:原始跨语言对齐已经存在磁盘上。**

Stage-A 记录(`formal_accepted_manifest.jsonl`)的 `target_support` 字段里,
每个目标词都带:

```json
{"target_index":0, "target_text":"你好",
 "raw_support_end_ms":480,        ← 单调化【之前】
 "support_end_ms":480,            ← 单调化【之后】
 "alignment_confidence":0.7227,
 "source_links":[{"source_index":0,"confidence":0.7227,"method":"neural_mutual_nearest"}]}
```

`source_links[].source_index` 的序列就是论文要的 Â。**直接算出来(3000 条):**

| | 均值 | 中位 | p90 | NIR=0 占比 |
|---|---:|---:|---:|---:|
| **我们的池(未分层)** | **11.64%** | 8.89% | 25.49% | 15.0% |
| 论文 NIR 分层池 En→Zh | 13.79% | — | — | — |
| 论文随机选 En→Zh | 9.66% | — | — | — |

**我们的池落在他们随机选(9.66)和分层选(13.79)之间 —— 差别不在难度水平,
在于我们完全不控制这个分布。**

另外单调化本身改动很大:`raw_support_end_ms` 与 `support_end_ms` 的最大差
**中位 2000 ms、p90 4641 ms、最大 12240 ms,86.9% 的样本被改动过**。
说明池子里确实有大量重排被压平了 —— 正是论文说会伤害低延迟档的那种。

**所以第 1 条 = 写一个纯 CPU 的打分/分桶脚本 + 重建采样清单,不需要 GPU、
不需要装包、不需要重跑对齐。**

## 第 3 条可能已部分满足

我们的 `target_semantic_delta` 是按事件切的,而事件对应目标文本块
(实测:`'我'`→16 码、`'完全同意'`→52 码,约 260 ms/字),
`micro_write_events` 里还带 `target_word_start/end` 和 `semantic_start/end`。
**所以码本来就是按目标词块切的。**

真正的问题不在数据,而在**推理时 END_SEMANTIC 落点**:C 的终止率是 1.000
(它确实停在 END_SEMANTIC 上),但实测 69–79% 的切口仍在满音量处 ——
**说明模型学到的片段边界与自然短语边界不一致。** 这仍然是训练问题,
但描述要改成"让 END_SEMANTIC 落在词块边界上",而不是"把码重新切分"。

## 建议的执行形态

**一次数据重建 + 一次训练**,同时包含 1、2、3(+ 可选 4):

1. **纯 CPU 前置**(可立刻开始,不占 GPU):
   * 从 `target_support` 算每条样本的 NIR,按 NIR × 句长分桶;
   * 按论文权重 `{high:0.1, mid_high:0.3, mid_low:0.4, low:0.2}` ×
     `{short:0.1, medium:0.5, long:0.4}` 重采样出新的训练清单;
   * 把 gold 事件重分箱到固定 chunk(建议 640 ms,IDLE 率 50.7% 最平衡),
     无内容的 chunk 监督成"立刻输出终止符"。
2. **一次训练**:从 C 的 `iter_0004236` 继续,纯 CE,按既定的 100/200 步早评 +
   400 步节奏。
3. 验收判据见正文。
