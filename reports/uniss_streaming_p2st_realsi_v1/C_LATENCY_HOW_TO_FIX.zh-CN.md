# C 的延迟问题到底是什么,以及怎么解决

## 先纠正一个我一直在用的口径:LAAL 的差有 71–82% 是公式折扣

SimulEval 的 LAAL 是

```
LAAL = mean(d_i) − 步长 · (N−1)/2      步长 = 源时长 / max(N, 参考长度)
```

**N 是语音块数。N 越大,减掉的那一项越大 —— 而这一项与音频实际何时到达毫无关系。**
直接实测每个臂的 `mean(d_i)` 和它与 LAAL 的差:

| | LAAL | **mean(d) 实测** | 公式折扣 | 块数 N |
|---|---:|---:|---:|---:|
| C k1 En→Zh | 4437 | **4998** | 562 | 5.86 |
| C s1t0 En→Zh | 3686 | **4422** | 735 | 7.38 |
| **m3 δ=5 En→Zh** | **566** | **3866** | **3300** | 35.89 |
| C k1 Zh→En | 3681 | **4681** | 1001 | 5.53 |
| C s1t0 Zh→En | 2997 | **4203** | 1206 | 6.44 |
| **m3 δ=5 Zh→En** | **778** | **3790** | **3013** | 30.97 |
| C k25 En→Zh | 7313 | 7322 | 10 | 1.07 |

拆开 C 与 m3 δ=5 的 LAAL 差:

| | LAAL 差 | 其中公式折扣 | **其中真实到达差** |
|---|---:|---:|---:|
| C k1 → m3 δ=5(En→Zh) | 3871 | 2738(**71%**) | 1132 |
| C s1t0 → m3 δ=5(En→Zh) | 3120 | 2565(**82%**) | **556** |
| C s1t0 → m3 δ=5(Zh→En) | 2219 | 1807(**81%**) | **413** |

**所以:s1t0 之后,C 的音频平均到达时刻只比 m3 δ=5 晚 413–556 ms,而 LAAL 报出来是
晚 2219–3120 ms。** 我前几轮把 LAAL 当作延迟的头号数字来讲,那是不准确的 ——
在这个操作点上它主要由块数驱动。

**一个必须写下来的推论:C 只要把每次提交的文本切成更小的块发出去,LAAL 就会大幅
下降,而音频到达时刻不变甚至更晚 —— 那是刷指标,不是改善。所以不要做,而且以后对外
报 LAAL 必须同时报首次发音和 mean(d),否则数字会被误读。**

## 真实的差距是首次发音,而且它是真的

首次发音不含任何公式项,是纯粹的"听众多久之后听到第一声":

| 中位首个块 | C k1 | **C s1t0** | m3 δ=0 | **m3 δ=5** |
|---|---:|---:|---:|---:|
| En→Zh | 2240 | **1440** | 2400 | **320** |
| Zh→En | 2240 | **1440** | 2560 | **320** |

**s1t0 已经拿回 800 ms(2240 → 1440),剩下与 m3 δ=5 还差 1120 ms。** 这 1120 ms
是要解决的真问题。

## 这 1120 ms 卡在哪:提交链,而且被 ASR 的释放速率绑死

已测清的三件事:

1. **`首次开口 == MT 提交器首次释放`,80/80 = 100%** —— TTS 一点都不多等。
2. 拆开 2080 ms 的开口:**ASR 提交器 960 ms + MT 提交器再 1120 ms**。
3. **三档 holdback 下提交冲突全是 0** —— holdback 纯属保守,不是在避免冲突。

而块数低也是同一个原因。看提交速率:

| | 读步中位 | 块数 | **块/读步** | 字/块 |
|---|---:|---:|---:|---:|
| C k1 En→Zh | 45 | 5 | **0.111** | 5.0 |
| C s1t0 En→Zh | 45 | 6 | **0.133** | 4.0 |
| **m3 δ=5 En→Zh** | 45 | 34 | **0.756** | 1.7 |

**C 平均每 8 个读步才说一次话,m3 δ=5 是每 4 个读步说 3 次。**
但 C 的 0.111 不是策略保守造成的 —— s1t0 把 holdback 放到 0 也只从 0.111 到 0.133。
**它是源词速率的下界**:ASR 释放一个词 → MT 重译 → MT 的 LCP 长出一段 →
TTS 说一段。一条 45 步的句子里大约十来个词,就大约十来个释放周期。

**m3 δ=5 打破这个下界的方式是:δ 强迫它在每个事件都写 MT,不管源有没有增长 ——
于是它在音频之前就开始编。代价在表里:源 ASR 错误率 1.48、文本超生成 1.8 倍、
ASR-BLEU 1.36。** 这不是 C 缺的旋钮。

## 怎么解决,按"是否真实改善"排序

### 已完成:s1t0(纯配置,无训练)

RealSI 777 条实测:首次发音 **−971 / −830 ms**,mean(d) **−576 / −478 ms**,
ASR-BLEU 只花 **−0.65 / −0.32**。**建议设为默认。**

### 该做的第一件新事:训练 ASR 在均匀细读步上

这是唯一能同时降低**真实**延迟和提高质量的杠杆,因为开口被 ASR 的一致性绑住 ——
**ASR 更早达成一致,就同时买到更早的开口和更高的 BLEU**,不是取舍。

依据(全部已测):

| | 整段 | k25 | **k1** |
|---|---:|---:|---:|
| C 中文源 CER | 0.250 | 0.264 | **0.804** |
| C 英文源 WER | 0.363 | 0.390 | 0.421 |

中文在细读步上崩了 3 倍,英文几乎不动;m3 在同一切换上更严重(0.248 → 1.708);
第三方 ASR 读同样音频只要 0.141 / 0.159,**音频本身没问题**;C 的训练切在 gold
事件/词边界上,**从没见过固定细网格**。

做法:纯 CE 配方 + 一个均匀 160 ms 读网格的 ASR family,中文源加量。
收益已标价:分桶表显示把整批推进"错误率 < 0.15"桶,k25 是 **25.66 / 21.12**,
**En→Zh 已超过论文 m=4 的 25.54**。

### 一个还没试过的便宜实验:词边界提交

ASR 提交器现在是**字符级**的 `LCP(previous, current) − holdback`,holdback 是
砍掉固定的字符数。**改成"释放到最后一个完整词为止"**,在同样的风险下会释放得更早
(英文尤其明显 —— 砍 1 个字符和砍到词边界差别很大)。
之前试过的 `SeededPrefixCommitter`(给 previous 播种)不是这个,而且它更差;
**词级修剪没试过**。这是纯推理侧改动,几十行,值得先跑。

### 明确不要做的三件

1. **不要为了 LAAL 去碎片化输出** —— 已证明 71–82% 的 LAAL 差是块数折扣,
   碎片化只动数字不动音频。
2. **不要照搬 δ** —— m3 δ=5 已把这条路走到头:开口 320 ms,ASR-BLEU 1.36。
3. **不要调 pacer,不要单独修 TTS** —— margin 1200↔2000 的对照证明 pacer 是空操作;
   TTS 对开口的贡献已测为 0,且 C 的峰值 0.776–0.859、>4kHz 0.003 已与 m3 同级或更好。
