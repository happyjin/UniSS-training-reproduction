## 1. 主表 —— ASR-BLEU

`k=25` 是 25 × 160 ms = **4000 ms 读步,与论文 m=4 精确对齐**(网格里唯一零量化
误差的点)。`offline` 是整段一次读完,不流式。

**同口径差距:En→Zh 低 8.21 BLEU,Zh→En 低 8.06 BLEU。**

两种 BLEU 协议都报,因为论文既没说 sacreBLEU 版本也没说归一化。仓库协议(英
NFKC+小写+13a;中 OpenCC t2s+去标点+字符插空格)比原始高 1.6–2.9 分 ——
**这个差就是协议模糊性的实测量级**,引用单个数字会把它藏起来。

`placed`(按发出时刻放置、空隙留静音)与 `concat`(片段紧接)只差 0.03–0.04 BLEU,
所以打分 ASR 对插入的静音不敏感,主表用 `placed`。空假设 0/1554,`--score-empty-hypotheses`
已开(不开会静默丢掉失败样本、抬高分数)。

## 2. 差距归因 —— 流式策略的代价约等于零

这是本次最重要的结果。

| 层 | 测量 | 结论 |
|---|---|---|
| **流式策略** | k=25 **17.33 / 14.41** vs offline **17.34 / 14.43** | **差 +0.01 / +0.02,即零代价** |
| **领域难度** | 第三方 ASR 读 RealSI **源**音频:Whisper-large-v3 英文 **WER 0.141**,Paraformer-zh 中文 **CER 0.159** | 中等难度,不是不可能 |
| **我们的 ASR 段** | 我们级联的流式 ASR:英文 **WER 0.390**,中文 **CER 0.339** | **比同一份音频上的离线第三方 ASR 差 2.1–2.8 倍,多出 0.249 / 0.180 错误** |
| **欠生成** | 简洁惩罚 **bp 0.73** 两个方向;sys/ref 长度 8361/10509 与 6539/7101 | 系统性少说约 27% |
| TTS 段 | TTS 前 Text-BLEU 16.59 / 10.46,TTS 后 ASR-BLEU 17.33 / 14.41 | **TTS 后反而更高** —— 打分 ASR 把文本规整了(中文字符切分、英文小写),不是 TTS 在丢分 |

**所以那 8 BLEU 的差距压倒性地来自 ASR 段,不是流式机制。** 这一点有直接反证:
把流式完全关掉(offline)分数一点没涨。

**一个必须说明的量化事实:** RealSI 句级片段中位只有 6.2–7.1 秒,而 4000 ms 读步
意味着中位只有 **2 个读步**。所以 **k=25 本身就已经接近离线** —— 这解释了
"offline ≈ k25",也说明**论文的 m=4 "Sent" 行同样接近离线**,这一点上两边是公平的。
要看到真实的流式代价必须用更小的 k(k=6 是 960 ms,6.7 秒片段上有 7 个读步)。

**长度先验在 k=25 上大面积饱和。** 它的桶只到 24 字符,而 4 秒读步提交的文本远超

`--length-prior-scale 0` 的对照 arm,尚未跑。

## 4. 口径差异(逐条)

1. **块网格不同。** 论文读 1000 ms × m;我们读 160 ms × k。**k=25 = 4000 ms 是网格
   里唯一零误差的点**,其余点误差 0.8–4%,m=2 只能用 k=12/13 括起来(±4%)。整数
   步长是被 1280 样本的 GLM hop 强制的(否则前端会落在非 token 边界,破坏已验证的
   201/201 前缀因果性),所以这是结构性的,不是随意选的。
2. **m 是训练进去的,k 不是。** 论文明确写"训练轨迹按 m∈{1,…,12} 增强,使单个
   checkpoint 支持所有延迟档"。C 的训练样本切在 gold 轨迹的**事件/词边界**,
   从没见过固定读网格,更没有固定 m。所以我们的曲线**预期比它们的更不规则**,
   而长度先验饱和就是这种不规则的一个具体来源。
3. **系统不同,不是消融。** 我们是三段隔离的提示级联(ASR→MT→TTS)+ local-agreement
   提交器 + 外部 switch rule,时机刻意放在权重之外;论文是双流 Thinker–Talker
   加文本-码联合轨迹监督,骨干规模、数据量(约 2k 小时)、解码方式都不同。
4. **切分是给定的,不是自己检测的。** 我们用 RealSI 自己的 `segment` 边界(上游
   README 说这些段"convey complete semantic for translation" 并建议按此评测),这
   与 "Sent" 的含义一致 —— 但论文没说它是否也用这个切分,而 LiveInterpret 2.0 是
   要自己切分的部署系统。**所以我们的数字相对任何自切分系统是上界。**
5. **ASR backend 与论文一致但不完全可比。** 英文 Whisper-large-v3、中文
   Paraformer-zh,都是已缓存权重、零安装。但论文没说语言→模型的分配、sacreBLEU
   版本、分词器或归一化,而它自己的附录 G.2 就做过 ASR 敏感性分析。故两种 BLEU 都报。
6. **参考是人工同传,不是笔译。** `trg_text` 是现场译员的输出,系统性压缩和省略,
   会惩罚完整的翻译。论文承受同样的handicap,所以对比是公平的 —— 但这些绝对值
   不能和 CVSS-T 式的 BLEU 相比。
7. **音频降混。** 发布的 wav 是 16 kHz 立体声;实测 19/20 是有损编码的双单声道
   (相关 ≥0.9972,rms(L−R)/rms(L) ≤0.075),`zh2en-07-ent` 是真立体声(0.940 /
   0.346)。用均值降混,与 `asr_transcribe.load_audio_array` 的做法一致。
   那 53 条已打 `stereo_content` 标记。
8. **上游计数差 1。** zh2en 431 = 上游 431;en2zh **346** vs 上游 347。零空文本、
   零时间反常,所以差的那一条不在这个发布里,原因未知,已记录未吸收。
9. **训练/测试污染。** 文件名层面无交集(训练语料前缀是 CommonVoice_EN_ /
   DailyTalk_ / EN_B / HQ / LibriSpeech_ / NCSSD_R_* / VCTK_ / emilia_zh_,
   RealSI 是 `en2zh-01-tech` 式)。**但不能声称为零:**(a) Qwen 文本骨干的预训练
   语料未公开而 RealSI 转写是公开的;(b) **打分用的 Whisper-large-v3 和前端的
   GLM4 WhisperVQ 都在未公开的网络音频上训练过,可能包含这些录音** —— 打分器污染
   无法排除。
10. **延迟指标尚未产出。** SimulEval 1.1.0 的 scorer 桥已写好并自检通过(33 个
    scorer 加载成功,fixture 上 NCA AL/LAAL/AP/DAL = 1250/1250/0.5/1000,
    CA = 1450/1450/0.6/1200,scorer 文件 sha256 已记录),但本轮未接到 RealSI 产出
    上。**而且论文在 RealSI 上只报 ASR-BLEU、没有 LAAL 表**,所以延迟无法与它并列
    ——只能作为我们自己的曲线。

## 5. 结论

**同口径单点对比:我们比论文低约 8 BLEU(En→Zh 17.33 vs 25.54,Zh→En 14.41 vs 22.47)。**

**但差距的位置是确定的,而且不在我这个会话一直在修的地方:**

* **流式策略零代价** —— 关掉流式(offline)分数不变(+0.01 / +0.02)。
* **ASR 段是主因** —— 同一份音频,离线第三方 ASR 是 0.141/0.159,我们的流式 ASR
  是 0.390/0.339,**多出 0.18–0.25 的错误率**。而 MT 忠实地翻译这些错误
  (`load balancing scheme` → `look bouncing scheme` → `看起来在弹跳`)。
* **欠生成放大它** —— bp 0.73,少说 27%。
* **长度先验在 4 秒读步上饱和**(zh2en 93.2% 的读步),所以终止率和欠生成两项
  都部分是它的产物。

**下一步按性价比:**
1. `--length-prior-scale 0` 对照 arm(约 5 分钟),把先验饱和从结果里剥出来。
2. **k=6(960 ms)arm** —— 这才是真正流式的点(7 个读步),也是唯一能看出流式代价的
   位置;顺带补 k=19 / k=31 得到与论文 m3/m4/m5 三点并列的曲线。
3. **英文/中文流式 ASR 是真正的瓶颈,而且是唯一需要训练的一项。** 领域难度已经
   量出来是 0.14–0.16,我们是 0.34–0.39,中间那 0.2 是可争取的空间。

# 6. 延迟:StreamLAAL / LAAL

## StreamLAAL 在句级数据上等于 LAAL

论文里 **StreamLAAL 只用于 Figure 5 的长篇 ACL60/60-dev S2TT**;RealSI 句级
(Figure 3/4)用的是普通 **LAAL**。StreamLAAL 相对 LAAL 多出来的一步是**先用
mwerSegmenter 把未切分的假设流切成与参考句对齐的 utterance,再逐段算 LAAL** ——
本轮每条样本本来就是一句(RealSI 自己的 `segment`),那一步是恒等,
**所以下表的 LAAL 就是 StreamLAAL 在这个设定下的值**。

指标实现:SimulEval 1.1.0 的注册 scorer,不是自研。文件按摘要固定:
`latency_scorer.py` sha256 `2fbb749de96a0d361e673ce1b2c476dfc5f19a25c9a082bb71bed33e37d5e1fa`。
延迟单位按论文自己的命令(`--eval-latency-unit char` 用于中文目标):
→中文用 char,→英文用 word。

## 读法

**① k=25 在延迟意义上不是流式。块数 1.0–1.1,LAAL ≈ 整段时长** —— 到最后才一次
说完。这与 offline 的 LAAL 几乎相同(7313 vs 7388;6677 vs 6718),和 ASR-BLEU
的 offline ≈ k25 是同一件事的两个侧面。**RealSI 句级片段中位只有 6.2–7.1 秒,而
4000 ms 读步意味着中位 2 个读步,所以 k=25 结构上就接近离线。**

**② k=1 是真流式,而且质量-延迟取舍第一次可见:**

| | LAAL 降低 | ASR-BLEU 代价 |
|---|---:|---:|
| En→Zh:k25 → k1 | **7313 → 4437 ms(−2876)** | 17.33 → 14.66(**−2.67**) |
| Zh→En:k25 → k1 | **6677 → 3681 ms(−2996)** | 14.41 → 10.37(**−4.04**) |

方向单调、符合预期(读得更细 → 上下文更少 → 翻译更差),这是本项目第一条真正的
质量-延迟曲线。

**③ k=1 的终止行为反而更好:** 终止率 0.995 / 0.990,而 k=25 是 0.904 / 0.966。
一致于 §3 的观察 —— k=25 上长度先验有 44.5% / 93.2% 的读步落进最宽的桶,而
k=1 每步只提交少量文本,先验工作在它有效的区间内。RTF 1.70 / 1.54(k=25 是
1.09 / 1.01),这是更细读步的算力代价。

**④ 计算感知延迟(CA)比 NCA 高 1.0–1.2 秒**,因为 RTF > 1。这是未批处理的研究级
级联在单卡上的上界,不是可部署性声明。

## 与论文对比:只能对比 ASR-BLEU,不能对比延迟

**论文在 RealSI 上的 LAAL 只出现在 Figure 3/4 的横轴,没有数值表**(Table 3 只有
ASR-BLEU),而 StreamLAAL 只出现在 ACL60/60-dev 的 Figure 5。所以:

* **ASR-BLEU 可以并列**(§1),我们低约 8 BLEU;
* **LAAL 不能并列** —— 论文没有可引用的数值。下表的 LAAL 只能作为我们自己的曲线,
  以及未来任何对照的基线。

## 一处必须标注的指标缺陷

**AP 在本配置下不可用**(表中给出但不应引用):SimulEval 的 AP 是
`sum(delays) / (source_length × reference_length)`,它假设 `len(delays)` 与
`reference_length` 同量纲。我们的 delay 是**每个语音块一个**(k=1 时 5.5–5.9 个),
而 `reference_length` 是参考译文的字/词数(数十),两者相差一个量级,于是 AP 落到
0.04–0.25 而不是 [0,1] 里有意义的位置。**AL / LAAL / DAL 不受影响** —— 它们的步长
本来就是 `source / reference_length`(LAAL 用 `max(hyp, ref)`),正是为这种长度
不匹配设计的。

# 7. m3 在同一网格上的对照

m3 在 RealSI 上按 C 读的同一个 160 ms 盲网格重测了 777 条,结果和一处对指标口径的
修正写在 **[M3_VS_C_REALSI_K1.zh-CN.md](M3_VS_C_REALSI_K1.zh-CN.md)**。要点:

* m3 那个"延迟最低"来自 **gold 事件读取时刻表**(`run_worker.py:175` 是
  `for event in trajectory.events`;实测 gold 事件只占 160 ms 可能读点的中位
  0.429,15.8% 还是零长度读步,边界即 gold 词边界)。换到盲网格后它的 LAAL 从
  518/2184 ms 变成 4364/3615 ms。
* 同网格上 **LAAL 是平局**(m3 快 1.6–1.8%),而 **C 的首次发音快 274/426 ms、
  真实可听起始快 750/1040 ms、计算感知 LAAL 快 2818/3598 ms**。
* m3 在 **19.7% / 23.7%** 的样本上一个语音片段都不发,ASR-BLEU 是 **1.73 / 0.80**
  (C 是 14.66 / 10.37)。配速器 margin 1200→2000 的对照证明这不是配速器造成的。
* 顺带定位到 §6 那条不对称质量代价的机制:**C 的中文源 ASR 在细读步下崩塌**
  (CER 0.250 offline → 0.264 @k25 → **0.804 @k1**),英文几乎不变
  (0.363 → 0.390 → 0.421)。
