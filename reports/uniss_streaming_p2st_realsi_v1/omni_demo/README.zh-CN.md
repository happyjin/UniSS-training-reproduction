# SimulS2ST-Omni demo 音频(zh2en/414)上的三方试听

## 输入

从论文的 demo 页下载:
`https://hasaki321.github.io/SimulS2ST-Omni.demo/media/audio/human_eval/zh2en/source/414.wav`

* 原始下载文件:`data/external/simuls2st_omni_demo/zh2en_414.wav`
  (16 kHz,**双声道 float**,7.41 s,sha256 前缀 `46fea516cbb5421e`)
* 两个声道**完全相同**(相关 1.0000,`rms(L−R)/rms(L)` = 0.0000),是双单声道,
  所以均值下混就是原信号,没有内容损失。
* 送进模型的:`data/external/simuls2st_omni_demo/zh2en_414_16k_mono.wav`(16 kHz 单声道)
* `speaker_global` 现算自这条音频的前 32 个 BiCodec global code,写进
  `data/external/simuls2st_omni_demo/SELECTION.json`。

**源音频内容(第三方 Paraformer-zh 转写,作为参照)**:

> 对呃他就这个就就就显现了了是是你才要注意到这个呃自己的这个心心慌啊什么心跳啊之类的

是带大量口头语和重复的自然口语,而且**没有参考译文** —— 论文 demo 页只给源音频,
所以下面只能定性听,不能算 BLEU。

## 三个配置

| | 读步 | 关键设置 |
|---|---|---|
| **C 最佳流式** | 160 ms | `source_holdback=1, target_holdback=0`(s1t0,刚在 RealSI 777 条上验证的新默认) |
| **C 最佳质量** | 4000 ms | k25。它在 RealSI 上 BLEU 最高(17.33/14.41),但块数≈1,**延迟意义上不是流式** |

## 这条样本正好演示了聚合数字说的事

**m3 δ=5 在 320 ms 就开口,之后几乎每 160 ms 说一句,内部静音只有 10.8% —— 听起来
最"流畅"、最像同传。但内容是词语沙拉。** 它的源 ASR 假设本身就已经崩了:
`对呃呃他就我这个人叫就就有就险下了于是你像住一个到这个个呃自自己的的这个一些的戏或方啊什么新调啊之类的`。
这就是 RealSI 上 ASR-BLEU 1.36/0.50 的样子。

**C 等到 1760 ms 才开口,只发 5 块、内部静音 40.7%(听起来会卡),但输出是通顺可用的
译文。**

**还有一处细节正好对上之前的归因**:C 的 k25 译文 "so you need to notice your own
heart and heartbeat" **比 s1t0 的更忠实** —— s1t0 把源里的"于是你才要注意到"听成了
"医生已经注意到",于是译文里出现了原文没有的 "the doctor"。这正是
"**C 的中文源 ASR 在细读步下退化**"(CER 0.264@k25 → 0.804@k1)在单条上的表现,
也再次说明下一步该修的是 ASR 而不是 TTS 或提交策略。

## 文件路径

每个臂三个音频:

* `<arm>/stereo/omni_demo_zh2en_414.wav` —— **双声道试听:左=源,右=译音**,

# 追加:按听感反馈做的三项定位与修正

听感反馈是:m3 发音更早但翻译不对、**声音有拉长音**;`c_best_quality_k25` 发音太晚;
`c_best_streaming_k1_s1t0` **有卡顿**。三项都做了直接测量。

## ① m3 的拉长音 = 我漏了重复惩罚(已修)

判据:相邻 20 ms 帧的**对数谱余弦 > 0.95** 即判为"谱冻结"(声音被拖住)。

| | 谱冻结占比 | 最长冻结 | >4kHz | 峰值 |
|---|---:|---:|---:|---:|
| C s1t0(内置惩罚 1.3) | **0.000** | 0 ms | 0.004 | 0.553 |
| C k25(内置惩罚 1.3) | **0.000** | 0 ms | 0.003 | 0.563 |
| **m3 δ=5 无惩罚(我上一轮给的)** | **0.203** | **1360 ms** | 0.013 | 0.773 |
| **m3 δ=5 + rp=1.1(真实 demo 配置)** | **0.000** | **0 ms** | 0.005 | 0.772 |
| m3 δ=5 + rp=1.3 | 0.000 | 0 ms | 0.004 | 0.679 |

**m3 的语义解码是对 8192 个 BiCodec 码的纯 greedy argmax,没有温度、没有 top-k、
没有重复惩罚**(`biased_family_probe.py` 的注释本身就写明了这点,并说离线 phase3
基线用的是 `repetition_penalty: 1.1`)。m3 的 demo 目录 `streaming_demos_delta5_rp11`
也说明它的试听配置是 **δ=5 + rp=1.1**,**我上一轮只给了 δ=5,漏了 rp** ——
那 1.36 秒的拖音是这个遗漏造成的,不是 m3 的固有缺陷。

C 一个冻结帧都没有,因为它的运行时默认就带 `semantic_penalty=1.3, window=64`
(那是之前修复战役的产物,注释里记了 1.1+窗口8 会退化成周期 3 的码环、解码出峰值
0.0000 的纯静音)。

**新增可听文件**(拉长音已消除,延迟不变,首次发音仍是 320 ms):
`m3_best_d5_rp11_k1/stereo/omni_demo_zh2en_414.wav`

一处值得注意的连带效应:rp 只改语义解码,但**交织运行时里语义码和 MT 共用同一个
KV cache**,所以文本也跟着变了。变完仍是词语沙拉,翻译错误与 rp 无关。

## ② C k25 发音太晚 = 配置的结构后果,不是缺陷

读步 4000 ms,而这条只有 7.41 s → **总共只有 2 个读步**。第一个读步(4000 ms)没有
可说的提交文本,于是唯一的语音块落在 7410 ms,也就是整句放完之后。

**k25 不该当流式配置用** —— 它在 RealSI 上 BLEU 最高(17.33/14.41),角色是
"接近离线的质量参照"。它的音频本身是干净的:0 冻结,只有 1 个 440 ms 的洞。

## ③ C s1t0 的卡顿 = 文本还没到,而且语速旋钮救不了(已实测否定)

逐块时间线:

```
块1 发出@1760  播放 1760→2080  ( 320ms, 16token, 提交 4 字)  前空档 1760ms
块2 发出@3680  播放 3680→4080  ( 400ms, 20token, 提交 8 字)  前空档 1600ms
块3 发出@5760  播放 5760→8060  (2300ms,115token, 提交42 字)  前空档 1680ms
块4 发出@6720  播放 8060→9540  (1480ms, 74token, 提交16 字)  前空档    0ms
块5 发出@7410  播放 9540→11040 (1500ms, 75token, 提交28 字)  前空档    0ms
```

**根因是译文文本到得太晚:**

| 时刻 | 累计字 | 占全文 |
|---|---:|---:|
| 1760 ms | 4 | **4%** |
| 3680 ms(源过半) | 12 | **12%** |
| 5760 ms | 54 | 55% |
| 7410 ms(源结束) | 98 | 100% |

**源播到一半时 C 只有 12% 的译文。4 个字无论说多慢都填不满 1.9 秒的空档。**

**语速旋钮实测无效**(`--speed` 已加进跑批,默认 1.0 不改变任何已发表数字):

| speed | 语义 token | 最长洞 | ≥300ms 洞数 | 洞合计 | 尾部溢出 |
|---|---:|---:|---:|---:|---:|
| **1.0** | 300 | 1680 ms | 3 | 3680 | 3630 |
| 0.9 | 340 | 1700 ms | 3 | 3480 | **4270** |
| 0.8 | 311 | 1700 ms | 3 | 3720 | 3790 |
| 0.7 | 301 | 1660 ms | 3 | 3540 | 3450 |

**洞完全不动,尾部在 0.9 上还变长了。** 因为 speed 最多把 300 token 拉到 340
(13%),而填满那个空档需要把 4 个字拉 8 倍。**所以我上一轮设想的"用语速重新分配
语音"这条路,被这次测量否掉了。**

另一个也不成立的选项:**只是延后开口去换平滑**。C 的块 3/4/5 本来就是背靠背无空档的,
所以"从块 3 开始说"等于把开口推到 5760 ms —— 那就退化成 k25 的行为。
**这条样本上不存在既 1.76 秒开口又不卡顿的推理侧配置。**

## 三个臂的问题归到同一处

| | 怎么处理"文本还没到" | 结果 |
|---|---|---|
| **m3 δ=5** | 靠 δ 强迫每步都写,不管源是否增长 —— **在音频之前就编** | 320 ms 开口、几乎不停(洞全 ≤ 220 ms)、**内容是错的** |
| **C k25** | 等全部信息到齐 | 译文最忠实、**7410 ms 才开口** |
| **C s1t0** | 有多少说多少 | 译文可用、1760 ms 开口、**但前 5.7 秒只有 12% 文本,于是 3 个 1.6 秒的洞** |

**所以卡顿在推理侧无解,唯一的修法是让 ASR→MT 链更早放出文本 —— 即已经论证过的
"把 ASR 训在均匀 160 ms 读网格上、中文源加量"。** 它同时买到:更早开口
(开口被提交器绑住)、更少的洞(提交更密)、更高的 BLEU(错误率 <0.15 桶里
En→Zh 已达 25.66)。这是本轮听感测量给出的第三条独立证据。
