# m3 vs C:同一份 RealSI、同一个 160 ms 读步网格

> **⚠ 本文开头那句"m3 的延迟优势是 oracle 分段撑出来的"是错的,已撤回。**
> 在同一批 80 条内部样本上做了隔离实验:只把读取时刻表从 gold 换成均匀 160 ms,
> LAAL 从 3466 变成 3221(**反而好 7%**),首次发音 2087 → 1972,发声条数 69 → 75。
> **读取时刻表对延迟的影响接近零,方向还相反。**
> 旧数字之所以小,主因是 **① 指标的 delay 轴粒度(每-token vs 每-语音块,×2.9)、
> ② 源时长分布(LAAL 随时长近线性)、③ 那两条 demo 样本是 69 条里最快的第 1 和第 6 名**。
> 完整逐项分解见 **[WHY_M3_LATENCY_GREW.zh-CN.md](WHY_M3_LATENCY_GREW.zh-CN.md)**。
> 本文其余的对比结论(同网格 LAAL 平局、C 计算感知明显更好、m3 四分之一样本不发声、
> ASR-BLEU 1.73/0.80 vs 14.66/10.37、配速器不是原因)不受影响,仍然成立。

## 结论先说

**m3 那个"延迟最低"是 oracle 分段撑出来的。把它放到 C 读的同一个盲网格上,
延迟优势消失,而且首次发音反而比 C 差 274 / 426 ms。**

| | m3(gold 事件网格,内部 16 条) | m3(RealSI,160 ms 盲网格) | C(RealSI,同网格) |
|---|---:|---:|---:|
| 首次可听 短/长 | **883 / 978 ms** | 5470 / 5760 ms | **4720 / 4720 ms** |
| LAAL | **518 / 2184 ms** | 4364 / 3615 ms | 4437 / 3681 ms |

同一个模型、同一份权重、同一套配置,只把"什么时候被问'现在要不要说'"从 gold 词
边界换成每 160 ms 一次,LAAL 就从 518 ms 变成 3615–4364 ms。**这 7–8 倍的差不是
数据难度,是读取时刻表。**

## 为什么必须重测:m3 的读步来自 gold

读 `run_worker.py:175`,自由运行的主循环是:

```python
for event in trajectory.events:
    row = session.run_event(event, ...)
```

而 `run_event` 从事件里只取四个字段 —— `source_glm_start`、`source_glm_end`、
`source_end_ms`、`source_final`。**没有任何 gold 文本进入模型**:WAIT、
WRITE_ASR、WRITE_MT、WRITE_SEMANTIC、EOS 全是它自己在候选集上取 argmax。这一点
m3 是清白的,它确实是自由运行。

**但读取时刻表整个来自 gold,而 gold 时刻表不是均匀网格。** 在 3000 条正式 gold
轨迹、42108 个事件上实测:

| | 值 |
|---|---:|
| 事件数 / 160 ms 可能读点数 | **中位 0.429**(p10 0.327,p90 0.562) |
| 零长度读步(`glm_start == glm_end`,不进新音频) | **15.8%** |
| `source_end_ms` 不在 160 ms 网格上 | 6.1% |

举一条:`NCSSD_R_EN_0000000083` 长 6940 ms(43 个可能读点),只有 23 个事件,落在
160、320、960、1280、1440…… —— 320→960 跳过 4 个块。**那些边界就是 gold 的词/事件
边界。** 所以 m3 被问"现在要不要说"的时刻,恰好是一个词刚说完的时刻。它永远不需要
自己发现边界,也永远不会在词中间被问。这是 oracle 分段,它直接给延迟送分。

RealSI 没有 gold 事件,时刻表必须自己给。和 C 对比的唯一诚实选择就是 **C 读的那个
网格:每 160 ms 一个读步**(C 的 k1)。GLM 帧恰好 80 ms —— gold 轨迹上
`source_duration_ms / source_glm_length` = 79.51–80.00,且
`glm_length == ceil(samples/1280)` —— 所以一个 160 ms 读步就是 2 帧。

## 两路共享什么、只差什么

**共享:** 777 条冻结 RealSI 片段、160 ms 读步网格、WhisperVQ 前端与它的 GLM 嵌入
数学(`p2st_cascade.py:352-357` 与 `persistent_runtime._speech_embeddings` 是同样
三行)、BiCodec 流式解码器、发声时间线放置、SimulEval scorer、ASR-BLEU 链。

**只差:** 权重,以及权重被训练的那个运行时。C 走自己的级联,m3 走交织事件语法。
这个差就是要测的东西,不是这份报告该抹掉的东西。

m3 用的是它自己门禁的配置(`wait_then_export_and_gate.sh`:margin 1200 / tail 2000
/ 上限 384 / 每事件 4 片段 / 文本 48 token),不是 C 的配置。

## 三处必须点明的读法

### ① 延迟的排名反过来了,而且 LAAL 是平局

盲网格上 LAAL 是 4364 vs 4437 和 3615 vs 3681 —— **差 1.6% 和 1.8%,统计上就是
平局**。而**首次发音 C 快 274 / 426 ms,真实可听起始 C 快 750 / 1040 ms**。
内部门禁上 m3 是 883/978 对 C 的 2660/2340(m3 快 3 倍),**换到盲网格上排名整个
翻转**。所以"m3 延迟最低"这个结论只在 gold 事件网格上成立。

**计算感知(CA)差距更大:C 快 2818 / 3598 ms。** 原因在决策统计里 —— m3 在
45 个读步里 WAIT 43 次、写 ASR 42 次,却只写 2 次 MT 和 2 次 TTS。它每一步都跑一遍
ASR 生成,算力全花在不发声上。

### ② m3 在四分之一的数据上根本不出声

**68/346(19.7%)和 102/431(23.7%)的样本一个语音片段都没有发**;算上解码后无有声
帧的,可听条数是 268/346 和 317/431。C 是 346/346 和 431/431。

TTS 触发率(TTS 事件 / 读步)中位只有 **0.062 和 0.043**。这不是配速器压住的 ——
见 ③ —— 是策略就没选 WRITE_SEMANTIC。

**终止率 Zh→En 是 0.000**:每一个语音片段都是撞上限停的,没有一个停在
END_SEMANTIC 上。这就是 m3 那个已知的收尾失败(`natural_eos` 在 iter 1132、1207、
2264 上一律 0.50)在 RealSI 上的样子,而且中文→英文方向更彻底。

### ③ 陷阱:m3 的"内部静音更低"是假象

m3 内部静音 0.098 / 0.017,C 是 0.302 / 0.309,看起来 m3 流畅得多。但:

* **片段中位 m3 是 2,C 是 5** —— 片段少,能产生的内部空隙自然少;
* **首片段中位 127 / 164 个 token = 2.5–3.3 秒语音一次性倒出来**,这不是流式,
  是攒够了一起说;
* **内部静音的中位数只统计有声文件** —— m3 那 22–26% 全静音的样本根本不进这个
  统计,而它们恰恰是最坏的情况。

所以低内部静音的正确读法是"更少、更大、更晚的语音块",不是"更平滑的流式"。
同理 Zh→En 的"排队最大 0 ms":它不排队,因为它几乎不发声。

## 配速器不是原因(margin 1200 → 2000 对照)

m3 有 39.3% / 46.7% 的片段撞在配速预算上,所以必须排除"是 C 的 margin 更宽才赢"
这个可能。把 m3 的 margin 从它门禁的 1200 换成 C 的 2000,重跑 777 条:

| | ASR-BLEU | 首次发音 | 可听条数 | LAAL |
|---|---:|---:|---:|---:|
| En→Zh 1200 → 2000 | 1.73 → **1.84** | 2818 → **2818** | 268 → **268** | 4364 → 4334 |
| Zh→En 1200 → 2000 | 0.80 → **0.83** | 2999 → **2999** | 317 → **317** | 3615 → 3605 |

**BLEU 动了 0.11 和 0.03,首次发音一个 ms 都没动,可听条数完全相同。**
配速器出局。而且首片段中位 127/164 token 时预算是 (2818+1200)/20 = 200 token ——
**开口时刻从来不是配速器决定的**。

## 分层归因:差在哪一段

同一份去标点代码,在同一批样本上重算:

| | m3 源 ASR | C 源 ASR | m3 MT 文本 BLEU | C MT 文本 BLEU |
|---|---:|---:|---:|---:|
| En→Zh(英文 WER) | **1.442** | 0.421 | 3.01 | **17.65** |
| Zh→En(中文 CER) | 0.842 | 0.804 | 1.75 | **11.44** |

**m3 的英文 ASR 错误率 1.442 —— 超过 100%,插入主导**(sys/ref 字数 14803/11510,
它在往外吐词)。空 MT 输出 68/346 和 100/431,C 是 0/346 和 0/431。
所以 m3 的崩塌是从 ASR 段就开始,一路复合到 MT 和 TTS,不是单独某一段的问题。

## 顺带确认的一件事:C 的中文 ASR 在细读步下崩塌

用同一份代码横跨 C 的三个臂:

| | 英文 WER | 中文 CER |
|---|---:|---:|
| offline(整段) | 0.363 | **0.250** |
| k25(4000 ms 读步) | 0.390 | **0.264** |
| **k1(160 ms 读步)** | 0.421 | **0.804** |

**中文 CER 从 0.264 跳到 0.804,英文只从 0.390 到 0.421。** 这解释了上一节报的那个
不对称质量代价 —— k25→k1 时 Zh→En 掉 4.04 BLEU 而 En→Zh 只掉 2.67:**掉的是中文源
ASR,不是翻译也不是声码器。** 这是 C 下一步该修的地方,而且是一条具体的线索:
中文前端在 160 ms 粒度上不成立,而英文可以。

## 对上一节 §6 的一处修正

上一节把 k1 的 `StartOffset` 2544 / 2573 ms 当作首次发音报出,那是对的
(SimulEval 的 StartOffset 就是首个片段的发出时刻,因为首片段不排队,
`start = max(earliest, 0) = earliest`)。但项目内部报告里还有第二个量
**"真实可听起始"** —— 它是 `audio_quality.leading_silence_ms`,发声时间线音频上
**第一个有声帧**的能量口径,和片段起始不是一回事。C 的 k1 是 **4720 / 4720 ms**,
比片段起始晚 2176 / 2147 ms。两个量本报告都给了,不要混用。

## 这份结果不能说什么

* **不能说 C 的延迟好**。C 的 LAAL 3681–4437 ms、真实可听起始 4720 ms,在 6–7 秒的
  句子上仍然很高;它只是**不比 m3 差**,而且在首次发音上略好。
* **不能拿去和论文并列**。论文的 RealSI LAAL 只在 Figure 3/4 的横轴上,没有数值表。
* **不能说 m3 的方案错了**。这份结果说的是:m3 的延迟数字依赖 gold 读取时刻表,
  一旦换成盲网格就不成立;它的策略在盲网格上有四分之一的时间不说话。
  m3 的交织语法本身是否可行,需要它在盲网格上重训才能回答 —— 它从没在盲网格上
  训练过,这也是它这里表现差的一个合理解释。
