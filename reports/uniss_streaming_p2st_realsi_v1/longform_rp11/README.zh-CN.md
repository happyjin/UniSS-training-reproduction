# audio_timeline_rp11 是 gold 时刻表的产物 —— 它是 cheating,这里给出严格流式版

## 一、gold 时刻表是 cheating,而且能量化偷了多少

`audio_timeline_rp11` 的配置从 `probe_rp11/PROBE_CONFIG.json` 里读出来是:

```
candidate_hf             = continue_end_m3 ... iter_0001132     ← 同一个
continue_write_bias      = 5.0                                  ← 同一个
family_mt_bias           = 0.0                                  ← 同一个
pace_margin_ms           = 1200                                 ← 同一个
mt_holdback              = 2                                    ← 同一个
max_s2s_semantic_tokens  = 1024                                 ← 与 m3_best_d5_rp11_k1 的 384 不同
读取时刻表                 = gold 事件(run_worker 的 for event in trajectory.events)
```

**它跑在 gold 事件时刻表上。** 从 worker 报告直接读出来的证据:

| | 实测 |
|---|---|
| 事件间隔 | 160 / 320 / 480 / 800 / 1120 / **1280** ms,**不规则** |
| 每事件放进的 GLM 帧数 | 2 / 4 / 6 / 10 / 14 / **16**,**按内容变化**(均匀网格恒为 2) |
| 零长度读步 | 有(`source_glm_start == source_glm_end`,不进新音频) |
| 事件数 / 160 ms 可能读点 | **0.340 – 0.648** |

**这四条在部署时一条都拿不到:真实场景是按固定时钟读音频,没人告诉你词在哪里结束、
这一步该放进多少音频、哪一步可以不放。** 所以 gold 时刻表提供了部署场景不存在的信息 ——
按定义是 cheating。

## 二、偷了多少:6–7 倍的 ASR 错误率,86–92% 的 BLEU

8 条长音频(16.5–19.4 s,域内 validation),**其余配置逐项相同**,只换读取时刻表:

| | **gold 时刻表** | **严格 160 ms 均匀网格** | 差 |
|---|---:|---:|---|
| **源 ASR 错误率** En→Zh | **0.258** | **1.618** | **6.3×** |
| **源 ASR 错误率** Zh→En | **0.086** | **0.641** | **7.5×** |
| MT 文本 BLEU En→Zh | 10.10 | **1.37** | **−86%** |
| MT 文本 BLEU Zh→En | 19.10 | **1.59** | **−92%** |
| ASR-BLEU En→Zh | 10.36 | **1.32** | −87% |
| ASR-BLEU Zh→En | 14.64 | **1.14** | −92% |
| TTS 保真度 En→Zh | 0.677 | 0.413 | −39% |
| TTS 保真度 Zh→En | 0.512 | 0.341 | −33% |
| 语音块数 | 39.5 | 92.5 | 2.3× |
| 首次发音 | 640 ms | **240 ms** | 更早 |
| 谱冻结 / 最长冻结 | 0.088 / 180 ms | 0.066 / 240 ms | 相当 |

**一个必须点明的悖论:换到均匀网格后 m3 开口更早(640 → 240 ms)、块更多
(39.5 → 92.5),表面上"更流式"—— 但内容塌到 BLEU 1.3。** 也就是说
gold 时刻表买的从来不是延迟,是**识别正确性**。

**片段上限不是原因:** cap 1024 与 cap 384 在均匀网格上**逐项相同**
(BLEU 1.37/1.59 对 1.37/1.59,块数、语义 token、峰值全同),说明 1024 从未咬到过。
两次推理的差别实质上只有读取时刻表这一条。

## 四、audio_timeline_rp11 本身的音质怎么样

在它自己那批(gold 时刻表)上,rp=1.1 确实是当时几个变体里最好的:

| 目录 | 谱冻结 | **最长冻结** | 峰值 | >4kHz | 最长静音 | ≥300ms 段 |
|---|---:|---:|---:|---:|---:|---:|
| `audio_timeline_greedy`(无惩罚) | 0.180 | **2340 ms** | 0.886 | **0.118** | 2260 | 3.5 |
| **`audio_timeline_rp11`** | 0.162 | **180 ms** | 0.912 | 0.037 | 1460 | 5.0 |
| `audio_timeline_rp11w8` | 0.136 | 180 ms | 0.950 | 0.039 | 1940 | 3.5 |
| `audio_timeline_rp11w16` | 0.155 | 380 ms | 0.910 | 0.033 | 2140 | 5.8 |
| `audio_timeline_rp105w64` | 0.131 | 160 ms | 0.950 | 0.043 | 3180 | 4.8 |
| **`audio_gold_timeline`**(天花板) | 0.138 | **160 ms** | 0.791 | **0.014** | 6160 | 3.8 |

**重复惩罚把最长拖音从 2340 ms 压到 180 ms,与 gold 天花板的 160 ms 同级** ——
这是当时选 rp=1.1 的正确理由。但仍有一条残留缺陷:`LibriSpeech_0000213211` 的
>4kHz 能量是 **0.270**(天花板 0.014),就是历史报告里那个"电音"。

注:长音频上连 gold 天花板的谱冻结都有 0.138 —— 20 ms 帧的 0.95 阈值会把正常的长元音
也算进去,所以**在长音频上只有"最长冻结段"有判别力,占比没有**。

## 五、文件路径

**严格流式版(你要的,按 audio_timeline_rp11 的推理设置但用真实场景时刻表):**

```
reports/uniss_streaming_p2st_realsi_v1/longform_rp11/
├── rp11_uniform_cap1024/stereo/<样本>.wav   ← 严格 160 ms 均匀网格,cap1024
├── rp11_uniform_cap384/stereo/<样本>.wav    ← 同上但 cap384(与 cap1024 逐项相同)
├── rp11_gold_cap1024/stereo/<样本>.wav      ← 复现当时的 gold 时刻表版(对照)
└── gold_ceiling/stereo/<样本>.wav           ← gold 码 → 同一解码器(TTS 天花板)
```

立体声都是**左=源,右=译音**;三个 m3 臂的右声道严格按真实发出时间线放置。
单声道在各臂的 `translation_concat/` 和 `translation_placed/`。

8 个样本:`LibriSpeech_0000079616`、`LibriSpeech_0000104521`、`LibriSpeech_0000174311`、
`LibriSpeech_0000213211`(以上 en2zh)、`emilia_zh_0003927983`、`emilia_zh_0003929091`、
`emilia_zh_0003980703`、`emilia_zh_0003980934`(以上 zh2en)。
其中 4 条(`LibriSpeech_0000174311`、`LibriSpeech_0000213211`、`emilia_zh_0003929091`、
`emilia_zh_0003980703`)正是当时 `audio_timeline_rp11` 里的那 4 条,可以直接 A/B。

## 六、结论

**是的,gold 时刻表是 cheating,而且是本项目里 m3 所有"看起来还行"的数字的来源。**
把它换成真实场景的固定 160 ms 时钟后,同一份权重、同一套 δ=5+rp1.1 配置,
源 ASR 错误率从 0.258/0.086 涨到 1.618/0.641,BLEU 从 10.10/19.10 塌到 1.37/1.59。

**所以此后 m3 的任何数字都必须在均匀网格上报。** 之前 §"m3 门禁 ASR 0.037"
那类数据只能作为"给它 oracle 分段时的上限",不能作为流式能力。
