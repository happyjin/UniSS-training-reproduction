# 为什么刚生成的音频都有割裂感

**结论:不是解码器,不是咔哒声,是发声时间线里插入的静音 ——
C 的时间线有 24–53% 是静音,每条 2.4–5.6 个空档,最长 7.1 秒,
而且 69–79% 的切口发生在满音量的语音中间。**

## 一、先排除解码器

`StreamingBiCodecDecoder` 其实做得很稳:`left_context_tokens=50`(每次带 50 个
token 的左上下文重解)、`holdback_tokens=5`(延后 100 ms 再吐,让尾部有更多上下文)、
`overlap_ms=80`(**80 ms 等功率交叉淡化**)。

实测**连续拼接版(`translation_concat`)在片段接缝处不断裂**。接缝前后 30 ms 的
对数谱余弦,对照是同一条音频的随机位置:

| arm | 接缝数 | 接缝谱余弦 | 对照谱余弦 | 接缝能量比 | 对照能量比 |
|---|---:|---:|---:|---:|---:|
| C 160 ms | 145 | **0.861** | 0.851 | 1.33 | 1.29 |
| C 960 ms | 67 | **0.894** | 0.834 | 1.21 | 1.42 |
| m3 160 ms | 704 | 0.848 | 0.846 | 1.64 | 1.46 |
| **m3 1920 ms** | 48 | **0.736** | 0.834 | **2.32** | 1.45 |

**C 的接缝比随机位置还平滑一点。** 只有 m3 在 1920 ms 上接缝确实更差
(片段少而大,交叉淡化覆盖不了那么大的韵律跳变)。

## 二、也不是咔哒声

在精确切口位置量样本级阶跃,并与语音内部相邻样本跳变的 p99 相比:

| arm | 空档数 | 切断处 \|x\| | 恢复处 \|x\| | p99 跳变 | **阶跃/p99** |
|---|---:|---:|---:|---:|---:|
| C 160 ms | 42 | 0.0330 | 0.0363 | 0.1022 | **0.44** |
| C 960 ms | 40 | 0.0468 | 0.0467 | 0.0912 | **0.44** |
| m3 160 ms | 134 | 0.0143 | 0.0152 | 0.0661 | **0.23** |

**全部 < 1**,即切口处的阶跃小于语音自身的最大样本跳变,**不会产生宽带咔哒**。
所以加淡入淡出并不能解决问题 —— 没有咔哒可消。

## 三、真正的原因:时间线里插入的静音

| arm | 语音合计 | 时间线长度 | **静音占比** | 空档数/条 | **最长空档** |
|---|---:|---:|---:|---:|---:|
| **C 160 ms** | 15.91 s | 20.83 s | **24%** | 5.2 | **3140 ms** |
| C 320 ms | 13.90 s | 21.32 s | **35%** | 5.6 | 3160 ms |
| C 480 ms | 14.36 s | 20.82 s | 31% | 4.0 | 3840 ms |
| C 960 ms | 14.28 s | 22.76 s | **37%** | 5.0 | **7400 ms** |
| C 1920 ms | 10.94 s | 23.23 s | **53%** | 2.4 | 7100 ms |
| m3 160 ms | 14.95 s | 16.99 s | **12%** | 16.8 | 620 ms |
| m3 1920 ms | 10.83 s | 18.08 s | 40% | 4.9 | 2400 ms |

而且切口不是切在停顿上。切口前后 20 ms 的 RMS(按整条 RMS 归一化):

| arm | 切前能量 | 切后能量 | **切前 > 0.5(即切在有声段中间)** |
|---|---:|---:|---:|
| C 160 ms | 0.95 | 0.87 | **74%** |
| C 320 ms | 0.90 | 0.89 | 71% |
| C 480 ms | 1.01 | 1.06 | 69% |
| C 960 ms | 1.17 | 1.00 | **78%** |
| C 1920 ms | 1.12 | 1.11 | **79%** |
| m3 160 ms | 0.59 | 0.50 | 63% |
| m3 1920 ms | 0.27 | 0.11 | 38% |

**C 有 69–79% 的空档是在满音量(0.90–1.17 倍全曲 RMS)处被切断的**,
静音 430–1420 ms(最长 7.4 秒),再从满音量突然回来。
**这就是耳朵听到的"割裂":不是杂音,是话说到一半被掐掉。**

**注意 m3 160 ms 的静音占比只有 12%、最长空档 620 ms —— 它听起来最连贯。**
但那是因为它在不停地编内容(ASR 错误率 1.62),不是因为它的音频更好。

## 四、根因是内容不是音频

空档出现的地方就是**模型当时没有可说的文本**的地方。之前在 demo 样本上量过:
源播到一半时 C 只有 12% 的译文(累计字数 4 → 12 → 54 → 98)。
`place_on_timeline` 只是忠实地把这件事呈现出来。

**所以割裂感在渲染侧无解:**
* **加淡化没用** —— 阶跃只有 p99 的 0.23–0.44,本来就没有咔哒;
* **拉慢语速没用** —— 已实测(speed 0.7/0.8/0.9 上最长空档纹丝不动,尾部还变长);
* **延后开口只是换成 k25 的行为**。

唯一的解法仍然是让 ASR→MT 链**更早、更密地放出文本**。

## 五、你可以自己做的 A/B(确认这个诊断)

同一条样本,两个文件:

```
# 连续拼接 —— 没有任何插入静音,应该听不出割裂
reports/uniss_streaming_p2st_realsi_v1/chunk_sweep/c_k1/translation_concat/LibriSpeech_0000079616.wav

# 发声时间线 —— 就是你听到割裂的那个
reports/uniss_streaming_p2st_realsi_v1/chunk_sweep/c_k1/translation_placed/LibriSpeech_0000079616.wav
```

**如果 concat 听起来连贯而 placed 割裂,就证实了:音频合成是好的,断的是内容供给。**
每个臂下面都有这两个目录,`stereo/` 的右声道用的是 placed 版。

## 六、一处提醒

**这两个文件的内容完全相同、时长不同。** concat 是"把系统说过的话连起来听",
placed 是"在真实时间线上听到的样子"。**报指标要用 placed(它才是真实体验),
判断音频合成质量要用 concat(它才隔离了合成本身)。**
